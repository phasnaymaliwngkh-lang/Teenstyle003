## ⚠️ ทำไมวัดบนฐานข้อมูล dev ไม่ได้

ฐานข้อมูล dev มีสินค้า 12 ชิ้นและคำสั่งซื้อ 0 ใบ → **ทุกคิวรีเร็วเท่ากันหมด**
และ PostgreSQL เลือก Seq Scan ทุกครั้งเพราะตารางเล็กกว่าที่ index จะคุ้ม
คิวรีที่โตแบบ `O(สินค้า × ออเดอร์)` กับคิวรีที่โตแบบคงที่จึงให้ตัวเลขเท่ากัน
จนกว่าจะมีข้อมูลจริง — **ปัญหาทั้งหมดในเอกสารนี้มองไม่เห็นเลยตอน dev**

## แพตเทิร์นที่เป็นต้นเหตุ: subquery ที่อ้างแถวของตัวเอง (correlated subquery)

เขียนอ่านง่ายและ "ดูเหมือนคิวรีเดียว" แต่ PostgreSQL ต้องรันซ้ำ **ทีละแถวของตารางนอก**

```sql
-- ของเดิม: 5,000 สินค้า = 5,000 subquery (วัดได้ 83,168 buffer hits ในคิวรีเดียว)
SELECT count(*) FROM "Product" p
WHERE COALESCE((SELECT sum(GREATEST(i."quantity" - i."reservedQuantity", 0))
                FROM "ProductVariant" v JOIN "Inventory" i ON i."variantId" = v."id"
                WHERE v."productId" = p."id"), 0) = 0;
```

พบ 6 ที่ แก้ 2 แบบ ตามคำถามที่ถามจริง

| คำถาม                           | เขียนแบบไหน                          | ตัวช่วยในโปรเจกต์           |
| ------------------------------- | ------------------------------------ | --------------------------- |
| "มีของขายไหม" (มี/ไม่มี)        | `EXISTS` — หยุดที่ตัวเลือกแรกที่เจอ  | `HAS_AVAILABLE_STOCK_SQL`   |
| "ขายได้กี่ชิ้น" (ต้องใช้ตัวเลข) | รวมรอบเดียวเป็นตารางแล้ว `LEFT JOIN` | `AVAILABLE_STOCK_JOIN`      |
| "ขายดีแค่ไหน" / "ถูกใจกี่คน"    | รวมรอบเดียวเป็นตารางแล้ว `LEFT JOIN` | `SALES_JOIN` / `SAVES_JOIN` |

ทั้งหมดอยู่ใน [backend/src/models/availability.ts](../backend/src/models/availability.ts)
และ [backend/src/services/shop.service.ts](../backend/src/services/shop.service.ts)
**นิพจน์แบบ correlated ถูกถอดออกจากโปรเจกต์แล้ว — ไม่มีให้เรียกใช้อีก**

| ------------------------------ | ------------------------------------------------------ | ------------------------- |
| `Order(paymentStatus, paidAt)` | รายงานยอดขายทุกแบบ (ตัดรอบด้วย `paidAt` ตามกฎ STEP 26) | 42 → 5.8 ms · 107 → 38 ms |
| `Order(orderNumber)` GIN trgm  | ค้นเลขออเดอร์ที่หลังบ้าน                               | 64.7 → 4.2 ms             |
| `User(name)` GIN trgm          | ค้นออเดอร์ด้วยชื่อลูกค้า                               | 139 → 25.5 ms             |
| `User(email)` GIN trgm         | ค้นลูกค้า/ออเดอร์ด้วยอีเมล                             | ใช้ร่วมกับด้านล่าง        |
| `User(phone)` GIN trgm         | ค้นลูกค้าด้วยเบอร์โทร                                  | 68.5 → 2.3 ms             |

**`contains` ของ Prisma = `ILIKE '%คำค้น%'` ซึ่ง btree ใช้ไม่ได้เลย** จึงต้องเป็น GIN trigram
(extension `pg_trgm` — สร้างในไฟล์ migration เอง เพราะ Prisma ไม่ได้จัดการ extension ให้)

### index ที่ตั้งใจ "ไม่เพิ่ม" (วัดแล้วไม่ช่วย)

- **trigram ของ `Product.name` / `Product.sku` / `Product.tags`** — ที่ 5,000 สินค้า
  planner เลือก seq scan เองเพราะตาราง Product เล็ก (6 MB) การสแกนอุ่น ๆ ใช้ ~1 ms
  วัดแล้วได้ **0.9×** (ช้ากว่าเดิมเล็กน้อย) → เพิ่มไปก็มีแต่ค่าดูแลตอนเขียน
  **ถ้าแคตตาล็อกโตถึงหลักหมื่น ให้กลับมาวัดใหม่** (หรือย้ายไป full-text search ของ Postgres)
- **index ของ `Order(paymentStatus)` เพื่อรวมยอดทั้งร้าน** — เงื่อนไขตรงกับ 84% ของแถว
  index ไม่ช่วยอะไรกับคิวรีที่ต้องอ่านเกือบทุกแถวอยู่แล้ว

> **กฎ: ห้ามเพิ่ม index เพราะ "น่าจะช่วย"** — index ทุกตัวมีค่าใช้จ่ายตอน INSERT/UPDATE
> และ GIN แพงกว่า btree มาก · เพิ่มเมื่อวัดแล้วเห็นผลต่างเท่านั้น และบันทึกตัวเลขไว้

## ⚠️ OR ข้ามตาราง = index ใช้ไม่ได้ ไม่ว่าจะมี index กี่ตัว

ค้นหาที่ `/admin/orders` เดิมเป็น

```ts
OR: [
  { orderNumber: { contains: q } }, // ตาราง Order
  { user: { email: { contains: q } } }, // ตาราง User
  { user: { name: { contains: q } } }, // ตาราง User
];
```

PostgreSQL ต้อง join ทั้งสองตารางให้ครบก่อนจึงจะประเมิน OR ได้ → สแกน Order 60,000 แถว
\+ User 20,000 แถว **สองรอบ** (นับจำนวน + ดึงรายการ) · **ใส่ index trigram แล้วยังไม่ต่าง**
(วัดแล้ว 267 → 245 ms) เพราะแผนคิวรีไม่เปลี่ยน

แก้ด้วยการแยกเป็น `UNION` ของสองขา **ขาละตารางเดียว** → ทั้งสองขาใช้ index ได้ (267 → 4 ms)
แบ่งหน้าและนับจำนวนใน SQL เดียวกันด้วย `count(*) OVER ()` (แพตเทิร์นเดียวกับ `/shop`)

**กับดักที่ต้องระวังเมื่อเขียนแบบนี้:** เงื่อนไขอื่น (เช่นตัวกรองสถานะ) ต้องใส่ให้ **ครบทั้งสองขา**
ลืมขาใดขาหนึ่งจะไม่ error แต่คืนผลผิด — มีเทสต์ยิงเคสนี้ไว้ใน `admin-order.test.ts`
และพิสูจน์แล้วว่าถ้าถอดเงื่อนไขออกจากขาหนึ่ง เทสต์ล้มจริง

## ⚠️ ขนาด response ก็เป็นเรื่องประสิทธิภาพ

`/api/admin/stock-alerts` เคยส่ง **ทุกแถว** ที่ตกเกณฑ์ → **1.1 MB ต่อคำขอ** (3,659 รายการ)
ทั้งที่คนอ่านดูได้ไม่กี่สิบรายการ · ตอนนี้จำกัด 200 รายการ (ปรับได้ถึง 500 ด้วย `limit`)

ถ้าตัดรายการแล้วไม่บอก แอดมินจะเข้าใจว่าเตือนแค่เท่านี้ แล้วของที่เหลือถูกมองข้ามเงียบ ๆ
(กฎเดียวกับป้ายกระดิ่งของ STEP 16 ข้อ 8: ไม่รู้ ≠ ไม่มีปัญหา)

## สิ่งที่วัดแล้วพบว่า "ไม่ใช่ปัญหา" (จึงไม่แก้)

  ซึ่งต้องรอให้ Next รองรับคู่กับ nonce ต่อคำขอ
- **TTFB ของหน้าร้านบน production build** (ข้อมูลปริมาณจริง, cache เย็น): 25–190 ms
  และจนจบ stream 47–386 ms — `<Suspense>` ที่มีอยู่ทำให้โครงหน้าออกไปก่อนข้อมูลจริงแล้ว
- **JS ที่เบราว์เซอร์โหลดต่อหน้า**: 640 KB ก่อนบีบอัด (14 ไฟล์) ซึ่ง **430 KB เป็น runtime
  ของ React + Next ที่ทุกหน้าใช้ร่วมกัน** · ตรวจแล้วว่า zod + react-hook-form ถูกแยกเป็น

## Redis — ยังไม่มี และไม่แกล้งว่ามี

เครื่องนี้ติดตั้ง Redis ไม่ได้ (Windows Home → ไม่มี Hyper-V → Docker Desktop ต้องใช้ WSL2 ที่ยังไม่ได้ติดตั้ง)
การเขียน adapter ที่ **ทดสอบกับของจริงไม่ได้เลย** แย่กว่าการบอกความจริงว่ายังไม่มี จึงยังไม่ทำ

ผลที่ต้องรู้ก่อน deploy หลาย instance (STEP 38)

1. **rate limit นับแยกต่อ process** → limit จริง = `RATE_LIMIT_MAX × จำนวน instance`
   และ `strictRateLimiter` (20/นาที) ที่กัน endpoint ซึ่งมีค่าใช้จ่ายจริง (OpenAI) ก็หลวมตามไปด้วย
2. deploy ใหม่ = ตัวนับเริ่มจากศูนย์
3. `/health` รายงาน `redis: not-configured` ตามความจริงอยู่แล้ว
4. backend เตือนใน log ตอนบูตเมื่อ `NODE_ENV=production` และไม่มี `REDIS_URL`

ทางแก้ระหว่างนี้: ตั้ง rate limit ที่ชั้น proxy/ingress (nginx, Cloudflare)
เมื่อมี Redis แล้ว เปลี่ยน `store` ที่ [backend/src/middlewares/rate-limit.ts](../backend/src/middlewares/rate-limit.ts) **ที่เดียว**

## cache ของหน้าร้าน

`revalidate: 60` ที่ [frontend/src/services/catalog.service.ts](../frontend/src/services/catalog.service.ts)
ทำงานจริงและวัดผลได้ (หน้า `/shop` ที่ cache อุ่นตอบ ~30 ms แทนที่จะรอ API 30–150 ms ทุกครั้ง)

⚠️ **`tags` ที่ประกาศไว้ยังไม่มีใครเรียก `revalidateTag()`** — ตรวจทั้งโปรเจกต์แล้วไม่มีเลย

(พฤติกรรมที่โปรเจกต์รับไว้ตั้งแต่ STEP 5/23) · เก็บ `tags` ไว้เพราะเป็นจุดเดียวที่ต้องแก้
เมื่อทำการล้าง cache แบบเจาะจง และ **ห้ามยืด 60 วินาทีให้นานขึ้นก่อนที่การล้าง cache จะใช้ได้จริง**

## วิธีตรวจซ้ำ

```powershell
node scripts/audit-performance.mjs            # สร้างฐานข้อมูลใหม่ → เติมข้อมูล → วัด → ลบทิ้ง
node scripts/audit-performance.mjs --keep     # เก็บฐานข้อมูลไว้ไล่ดู EXPLAIN เอง
node scripts/audit-performance.mjs --reuse    # ใช้ฐานข้อมูลที่ --keep ไว้ (ข้ามการเติมข้อมูล ~50 วินาที)
```

สคริปต์ **ไม่แตะฐานข้อมูลของแอป** (สร้าง `teenstyle_perf_audit` แยก และปฏิเสธถ้าชื่อชนกับของแอป)
และ **เปิด backend ตัวจริง** ชี้ไปฐานข้อมูลนั้น ไม่ได้ก็อป SQL มาไว้ในสคริปต์ —
SQL ที่ก็อปไว้จะเพี้ยนจากโค้ดจริงเมื่อไรก็ได้ แล้วเครื่องมือจะกลายเป็นตัวโกหก

งบเวลาต่อเส้นทาง (`budgetMs`) ตั้งไว้ราว 2–3 เท่าของค่าที่วัดได้ตอนปิด STEP 34
**ไม่ใช่ "เร็วที่สุดที่ทำได้" แต่เป็นเพดานที่ถ้าเกินแปลว่ามีอะไรผิดเชิงโครงสร้าง**
พิสูจน์แล้วว่าใช้งานได้จริง: ลองเอา subquery ต่อแถวของ `sort=bestselling` กลับไปใส่
เครื่องมือรายงาน 623 ms เกินงบ 400 ms แล้ว exit code เป็น 1

ให้เปิด log ของ PostgreSQL เอาเอง ซึ่งเป็นวิธีที่ใช้หาปัญหาทั้งหมดใน STEP 34

```sql
ALTER DATABASE teenstyle_perf_audit SET log_min_duration_statement = 0;
```

แล้วอ่านไฟล์ใน `<data_directory>/log` (บนเครื่องนี้คือ `C:/Program Files/PostgreSQL/18/data/log`)
จะได้ทั้งจำนวน statement ต่อคำขอและเวลาของแต่ละตัว
