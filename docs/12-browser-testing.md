# 12 — Browser Testing (STEP 39)

> ตรวจว่าเว็บ **ทำงานจริงในเบราว์เซอร์** ไม่ใช่แค่ตอบ 200

```bash
npm run dev                          # ต้องเปิดไว้ก่อน
node scripts/audit-chrome.mjs        # console · CSP · คำขอที่ล้ม · กดจริง · API ล่ม
node scripts/audit-responsive.mjs    # เลย์เอาต์ทุกหน้า (STEP 31)
```

## ทำไมต้องมีเครื่องมือนี้ ทั้งที่มีตัวตรวจอื่นอยู่แล้ว

| เครื่องมือที่มีอยู่       | มองไม่เห็นอะไร                                                          |
| ------------------------- | ----------------------------------------------------------------------- |
| `curl`                    | หน้าที่ JavaScript ถูก CSP บล็อกทั้งหมด **ยังตอบ 200**                  |
| `audit-responsive.mjs`    | วัดเลย์เอาต์ ไม่ได้ดูว่ามี error ใน console                             |
| `audit-seo.mjs`           | อ่าน HTML ชุดแรก ไม่ได้รอให้ hydrate                                    |
| เทสต์คอมโพเนนต์ (STEP 37) | รันใน jsdom — **ไม่มี CSP ไม่มี hydration จริง ไม่โหลด chunk ของ Next** |
| `audit-performance.mjs`   | วัดเวลาที่ backend ตอบ ไม่ได้เปิดหน้าเว็บ                               |

ช่องว่างที่เหลือคือ **"หน้าเปิดได้ แต่ใช้งานไม่ได้"** — ปุ่มยังเห็น เลย์เอาต์ยังสวย status ยัง 200
แต่กดแล้วไม่มีอะไรเกิดขึ้น นี่คือสิ่งที่ `audit-chrome.mjs` ตรวจ

## ตรวจอะไร

| ข้อ | ตรวจอะไร                            | ตัวชี้ขาด                                                         |
| --- | ----------------------------------- | ----------------------------------------------------------------- |
| 1   | exception ที่หลุดออกมา              | `Runtime.exceptionThrown`                                         |
| 2   | `console.error` / `console.warn`    | `Runtime.consoleAPICalled` — รวม **hydration mismatch ของ React** |
| 3   | **CSP บล็อกอะไรไปจริงไหม**          | ข้อความของเบราว์เซอร์เอง (`Log.entryAdded` source `security`)     |
| 4   | คำขอที่ล้มหรือได้ 4xx/5xx           | `Network.loadingFailed` + `Network.responseReceived`              |
| 5   | **status ของเอกสารตรงกับที่คาดไหม** | `expectStatus` ใน `ROUTES` — หน้า 404 ต้องตอบ 404 ไม่ใช่ soft 404 |
| 6   | **JavaScript ทำงานจริงไหม**         | กดปุ่มจริงแล้ว DOM ต้องเปลี่ยน                                    |
| 7   | **API ล่มแล้วบอกผู้ใช้ไหม**         | บล็อกคำขอไป backend แล้วต้องมี `role="alert"`                     |

### ข้อ 3 แทนการนับ nonce ในซอร์ส

STEP 28 กำหนดวิธีตรวจ CSP ไว้ว่า "จำนวน `<script>` ต้องเท่ากับจำนวนที่มี nonce" ซึ่งเป็น
**ตัวแทน** ของคำถามจริงที่ว่า "เบราว์เซอร์บล็อกอะไรไปไหม" · ตัวตรวจนี้ถามเบราว์เซอร์ตรง ๆ
พิสูจน์แล้วว่าจับได้จริงด้วยการแทรก `<script>` ที่ไม่มี nonce เข้าไปหนึ่งตัว แล้วได้รายงานว่า

> `Executing inline script violates the following Content Security Policy directive 'script-src 'self' 'nonce-…' 'strict-dynamic' 'unsafe-eval''`

### ⚠️ CSP ของ dev กับ production ไม่เหมือนกัน

dev มี `'unsafe-eval'` (HMR ของ Turbopack ต้องใช้) · production ไม่มี
→ **การตรวจ CSP ที่เชื่อได้ต้องรันกับ production build** (`npm run build && npm start`)
ตอน STEP 38 ตรวจกับ production build แล้วพบว่า `<script>` ทุกตัวมี nonce ครบทั้ง 4 หน้า

### ข้อ 7 ตรวจได้เฉพาะหน้าที่ดึงข้อมูลจากเบราว์เซอร์

การบล็อก URL ที่ชั้นเบราว์เซอร์ **ไม่มีผลกับ Server Component** เพราะคำขอนั้นออกจาก process
ของ Next ไม่ได้ออกจากเบราว์เซอร์ · เคยเข้าใจผิดตอนเขียนสคริปต์นี้ แล้วได้ผลว่า `/admin`
"ไม่มี alert" ทั้งที่หน้าโหลดข้อมูลได้ปกติ — **ผลตรวจที่ผิดแบบนี้อันตรายกว่าไม่ตรวจเลย**
ตอนนี้เล็งเฉพาะ `/admin/knowledge` · `/admin/support` · `/customer-service` (client component)
และผ่านทั้งสามหน้า

## ของที่เจอตอนเขียนเครื่องมือนี้ครั้งแรก (ทั้งหมดเป็นของจริง แก้แล้ว)

### 1. `/admin/knowledge` โหลดบทความไม่ได้เลย (422 ทุกครั้งที่เปิด)

หน้าขอ `limit=100` แต่ `knowledgeSearchQuerySchema` ของ backend จำกัด `max(50)`
→ ได้ **422 ทุกครั้ง** แล้วหน้าแสดงข้อความรวม "ไม่สามารถโหลดข้อมูลบทความคลังความรู้ได้"
จึงไม่มีใครรู้ว่าสาเหตุคืออะไร · เป็นหน้าที่ coverage ต่ำ (24% — ดู [11-testing.md](11-testing.md))
และไม่มีเทสต์ไหนเปิดหน้านี้เลย

**แก้:** ใช้ค่าคงที่ `ARTICLE_PAGE_SIZE = 50` ที่ไม่เกินเพดานของ API · ใช้ `describeApiError()`
เพื่อให้เหตุผลจริงจาก server ถึงแอดมิน (กฎ STEP 26 ข้อ 10) · และแสดงยอดจริงเมื่อรายการถูกตัด
(กฎ STEP 34 ข้อ 6)

### 2. ปุ่มในตาราง `/admin/knowledge` เล็กกว่า 44px — ที่ซ่อนอยู่หลังบั๊กข้อ 1

พอบั๊ก 422 ถูกแก้ ตารางบทความก็เรนเดอร์จริงเป็นครั้งแรก แล้ว `audit-responsive.mjs`
(ซึ่งรันผ่านมาตลอด) ก็เห็นปุ่มแก้ไข/ลบขนาด **32×32** และปุ่มสลับสถานะสูง **26px** ทันที

> **บทเรียน:** หน้าที่โหลดข้อมูลไม่สำเร็จทำให้ตัวตรวจอื่น ๆ "ผ่าน" เพราะไม่มีอะไรให้ตรวจ
> — เหมือนกรณี rate limit ของ STEP 31 ที่แผง error สั้นจนไม่ล้นแล้วผ่านแบบหลอก ๆ

### 3. Next เตือนว่ารูป LCP ไม่ได้โหลดแบบ eager (`/shop` และ `/looks`)

เพิ่ม prop `priority` ให้ `ProductCard` / `LookCard` แล้วใส่ให้ **การ์ดแรกใบเดียว**
(ใส่หลายใบจะแย่งแบนด์วิดท์กันเองแล้ว LCP แย่ลง)

## กับดักของตัววัดเอง (แก้แล้วทั้งสามข้อ)

1. **ตรวจ 0 หน้าแล้วบอกว่าไม่พบปัญหา** — `--only=/faq` ถูก Git Bash แปลงเป็น path ของ
   Windows (`C:/Program Files/Git/faq`) ตัวกรองจึงไม่ match อะไรเลย แล้ว exit 0
   → ตอนนี้ตรวจ 0 หน้า = exit 2 · **ใส่ `MSYS_NO_PATHCONV=1` เมื่อส่ง argument ที่ขึ้นต้นด้วย `/`**
2. **"backend ไม่ตอบ" ทั้งที่ตอบอยู่** — รันตัวตรวจติด ๆ กันจนชน rate limit ของ API เอง
   ได้ 429 แล้ว `waitForHttp` ถือว่ายังไม่ขึ้น → รอจนหมดเวลาแล้วรายงานผิดเรื่อง
   → ตอนนี้ตอบอะไรกลับมาก็ถือว่าขึ้นแล้ว และ **เตือนแยกเมื่อเจอ 429**
   ⚠️ `RATE_LIMIT_MAX` ใน `.env` มีผลเฉพาะตอนบูต — **แก้แล้วต้องรีสตาร์ต backend**
3. **เขียนไฟล์ผลไม่สำเร็จแล้ว exit 2** ทั้งที่ตรวจผ่านหมด → ตอนนี้เตือนแล้วไปต่อ

### ไม่มีบัญชีลูกค้า = ข้ามหน้าของลูกค้า ไม่ใช่ล้มทั้งตัว

ฐานข้อมูล dev ตอนนี้เหลือผู้ใช้คนเดียว (admin) ตัวตรวจเดิม **ล้มทั้งสคริปต์** ก่อนถึงหน้า guest ด้วย
ตอนนี้ข้ามหน้าของบทบาทที่ไม่มีบัญชี แล้วพิมพ์เตือนทั้งตอนเริ่มและในสรุป
→ ผลรอบล่าสุดจึงเป็น **33 เส้นทาง** ไม่ใช่ 44 · อยากตรวจครบต้องมีบัญชีลูกค้าที่มีคำสั่งซื้อจริง
