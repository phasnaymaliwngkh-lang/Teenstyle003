# 14 — Promotion / Coupon (STEP 41)

> คูปองส่วนลด · กฎการคิดเงิน · และสิ่งที่ยังไม่ได้ทำ

```
/checkout            → ช่องกรอกรหัสคูปอง + ยอดหลังส่วนลด (ต้องล็อกอิน)
/admin/coupons       → สร้าง/แก้/ปิดใช้งานคูปอง (coupon:manage = ADMIN ขึ้นไป)

POST /api/coupons/apply                 ตรวจคูปองกับตะกร้าของตัวเอง (20/นาที)
GET  /api/checkout/summary?couponCode=   ยอดหลังส่วนลด
POST /api/orders { couponCode }          ใช้คูปองจริง + จองโควตา
GET|POST /api/admin/coupons · PATCH|DELETE /api/admin/coupons/:couponId
```

## schema มีอยู่แล้วตั้งแต่ STEP 2 — STEP 41 คือการทำให้มันทำงาน

`Coupon` · `Order.couponId` · `Order.couponCode` · `Order.discountTotal` และ
ตารางเชื่อม `_CouponToProduct` / `_CategoryToCoupon` ถูกออกแบบไว้แล้ว **ไม่ต้อง migrate**
· seed ก็สร้างคูปองไว้ 3 ใบมาตลอด (`TEEN15` · `FREESHIP690` · `NEWBIE100`)
แต่ `discountTotal` ถูก hardcode เป็น `0` ทั้งในตะกร้าและตอนสร้างคำสั่งซื้อ
→ **คูปองทั้งสามใบไม่มีทางใช้ได้เลย** จนถึง STEP นี้ (STEP 9 ข้อ 7 จดไว้ว่าจะมาทำตอน STEP 41)

## กฎการคิดเงิน — อยู่ที่ [models/coupon.model.ts](../backend/src/models/coupon.model.ts) ที่เดียว

ทุกที่ที่ต้องรู้ว่า "คูปองนี้ลดเท่าไร" เรียก `evaluateCoupon()` ตัวเดียวกัน:
หน้าสรุปยอด checkout · ปุ่ม "ใช้คูปอง" · และ **การสร้างคำสั่งซื้อจริง**
ถ้าแยกกันคิด วันหนึ่งยอดที่โชว์กับยอดที่เก็บเงินจะไม่ตรงกัน แล้วไม่มีใครรู้ว่าอันไหนถูก
(ปัญหาเดียวกับกฎราคาที่เคยเขียนซ้ำ 4 ที่ตอน STEP 9 → รวมมาไว้ที่ `pricing.ts`)

| ชนิด            | คิดอย่างไร                                                        |
| --------------- | ----------------------------------------------------------------- |
| `PERCENTAGE`    | `ยอดที่เข้าเกณฑ์ × value / 100` แล้วจำกัดด้วย `maxDiscountAmount` |
| `FIXED_AMOUNT`  | `value` บาท แต่ไม่เกินยอดที่เข้าเกณฑ์                             |
| `FREE_SHIPPING` | ยกเว้นค่าจัดส่งเท่าที่คิดจริงในขณะนั้น                            |

### ยอดรวมทั้งสองแบบถูกยุบลง `discountTotal` ตัวเดียว

ตาราง `Order` มีช่องส่วนลดช่องเดียว และสูตรของบิลคือ

```
total = subtotal − discountTotal + shippingFee
```

คูปองส่งฟรีจึงกลายเป็น `discountTotal = ค่าจัดส่ง` แล้วหักกันพอดี
**ห้ามเพิ่มช่องส่วนลดช่องที่สองโดยไม่แก้สูตรนี้ให้ครบทุกที่** (รวมรายงานของ STEP 26
ที่อ่าน `discountTotal` ไปรวมยอด)

## กฎที่ห้ามละเมิด

1. **client ส่งได้แค่ `code`** — ไม่มีฟิลด์ส่วนลดหรือยอดเงินใน schema เลย ส่งมาก็ถูก Zod ตัดทิ้ง
   (มีเทสต์ยิง `discountTotal: 99999` + `total: 1` มาแล้วยืนยันว่าถูกเมิน)
   ยอดส่วนลดคิดใหม่ **ทุกครั้งตอนสร้างคำสั่งซื้อ** ไม่ใช่เชื่อยอดที่หน้าเว็บโชว์
2. **ส่วนลดห้ามเกินยอดสินค้าที่เข้าเกณฑ์** — ไม่งั้นยอดสุทธิติดลบ แปลว่าร้านต้องจ่ายเงินให้ลูกค้า
   (กฎเดียวกับสต็อกที่ห้ามติดลบของ STEP 6)
3. **จองโควตาด้วย SQL เดียวแบบมีเงื่อนไข ห้ามอ่านแล้วค่อยเขียน**

   ```sql
   UPDATE "Coupon" SET "usedCount" = "usedCount" + 1
    WHERE "id" = $1 AND ("usageLimit" IS NULL OR "usedCount" < "usageLimit")
   ```

   `rowCount = 0` → มีคนใช้ครบไปก่อน → โยน 409 → ทรานแซกชัน rollback ทั้งก้อน
   (แพตเทิร์นเดียวกับการจองสต็อกของ STEP 10 ข้อ 2)

4. **ยกเลิกคำสั่งซื้อต้องคืนโควตา** — เรียก `releaseCouponForCancelledOrder()` คู่กับการคืนสต็อก
   ทุกที่ (ลูกค้ายกเลิก · ร้านยกเลิก · หมดเวลาชำระเงิน · webhook ที่คืนของ)
   ถ้าไม่คืน `usedCount` จะค้างสูงกว่าการใช้จริง แล้วคูปองจะ "เต็ม" ทั้งที่ไม่มีใครได้ใช้
   → ลูกค้าถูกปฏิเสธด้วยเหตุผลที่ไม่จริง
5. **คูปองที่ใช้ไม่ได้ต้องบอกเหตุผล ไม่ใช่เงียบแล้วไม่ลดให้** — `CouponRejection` มี 9 เหตุผล
   แต่ละอันมีข้อความไทยของตัวเอง · รหัสที่ไม่มีอยู่จริงได้ **404** · รหัสที่มีแต่ใช้ไม่ได้ได้
   **200 พร้อมเหตุผล** เพราะผู้ใช้ต้องรู้ว่าติดเงื่อนไขข้อไหน (กฎเดียวกับช่องทางชำระเงินที่ปิด
   ของ STEP 11 ข้อ 1)
6. **ยอดขั้นต่ำเทียบกับยอดบิลทั้งใบ** ไม่ใช่เฉพาะส่วนที่คูปองคุม
   "ซื้อครบ 1,000 ลด 100" หมายถึงยอดบิล ไม่ใช่ยอดของหมวดที่คูปองคุม
   แต่ **ส่วนลดคิดจากยอดที่เข้าเกณฑ์** เท่านั้น (คนละตัวเลขโดยเจตนา — มีเทสต์แยกสองกรณีนี้)
7. **`coupon:manage` = ADMIN ขึ้นไป** — พนักงานหน้าร้านไม่ควรออกส่วนลดได้เอง
   เพราะเป็นการให้เงินออกจากร้าน (แพตเทิร์นเดียวกับ `analytics:read` ของ STEP 26 ข้อ 7)
8. **ลบคูปอง = soft delete** เพราะ `Order.couponId` ยังอ้างถึงแถวนั้น และประวัติต้องอธิบายได้ว่า
   คำสั่งซื้อเก่าได้ส่วนลดจากคูปองใบไหน · UI บอกว่าเป็นการเอาออกจากรายการ ไม่ใช่ลบถาวร
9. **สถานะของคูปองคำนวณสด ๆ ที่ server** (ใช้ได้ / ยังไม่เริ่ม / หมดอายุ / ปิด / ใช้ครบ)
   ไม่เก็บเป็นคอลัมน์ จึงไม่มีทางมีสถานะที่ไม่จริง (แพตเทิร์นเดียวกับการแจ้งเตือนสต็อกของ STEP 16)
10. **`POST /api/coupons/apply` คุมความถี่แบบเข้ม** เพราะเป็นช่องที่ไล่เดารหัสคูปองได้
    · เรียกจากเบราว์เซอร์เท่านั้น ไม่ใช่ Server Component (กฎ STEP 29)

คำสั่งซื้อที่สถานะ `PENDING_PAYMENT` **จองสต็อกไว้** (กฎ STEP 10 ข้อ 3)
ลบแถวออเดอร์ทิ้งเฉย ๆ ใน `afterAll` ทำให้ `Inventory.reservedQuantity` ค้างสูงขึ้นทุกรอบ
จนของ "หมด" แล้วเทสต์ล้มด้วยเหตุผลที่ไม่เกี่ยวกับโค้ด
— **เกิดขึ้นจริงตอน STEP 41: ค้างไป 18 ชิ้นโดยที่ตาราง `Order` ว่างเปล่า**
→ `afterAll` ต้องลด `reservedQuantity` ตามรายการของออเดอร์ที่ยังถือการจองอยู่ ก่อนลบแถว
(แพตเทิร์นเดียวกับเทสต์ COD ของ STEP 12 ที่ต้องลบ `InventoryMovement` ของตัวเอง)

## ยืนยันกับของจริงแล้ว

- สร้างคูปองผ่าน `POST /api/admin/coupons` จริง → **201** · `state = ACTIVE` · `usedCount = 0`
- เปิด `/admin/coupons` ด้วย session ของแอดมินจริง → **200** และหน้าเว็บแสดงรหัส สถานะ และยอดขั้นต่ำ
- `AdminLog` บันทึก `coupon.create` / `targetType = Coupon` (กรองได้ที่ `/admin/logs`)
- `audit-chrome` 34 หน้า 0 ปัญหา · `audit-responsive` 102 หน้า-ความกว้าง 0 ปัญหา
- ล้างข้อมูลที่ใช้ทดสอบออกหมด เหลือคูปองจาก seed 3 ใบ · reserved 0

## ที่ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ใช้คูปองได้ใบเดียวต่อคำสั่งซื้อ** — `Order.couponId` เป็นช่องเดียว การใช้หลายใบพร้อมกัน
  ต้องเพิ่มตารางใหม่และกำหนดลำดับการคิด (ซึ่งเปลี่ยนความหมายของ `discountTotal`)
- **ช่องกรอกคูปองมีที่หน้า `/checkout` เท่านั้น** ยังไม่มีที่หน้า `/cart`
  เพราะคูปองต้องรู้ค่าจัดส่งเพื่อคิดคูปองส่งฟรี ซึ่งหน้าตะกร้ายังไม่รู้ที่อยู่ปลายทาง
  (ค่าจัดส่งเป็น `null` จนกว่าจะรู้ที่อยู่ — กฎ STEP 9 ข้อ 7)
- **ยังไม่มีโปรโมชันอัตโนมัติ** (ลดเองโดยไม่ต้องกรอกรหัส เช่น "ซื้อ 2 แถม 1")
  STEP นี้ทำเฉพาะคูปองที่ลูกค้ากรอกรหัส
- **หน้าแอดมินยังไม่มีตัวเลือกจำกัดคูปองตามสินค้า/หมวด** ทั้งที่ API และการคิดเงินรองรับแล้ว
  (ต้องมีตัวเลือกสินค้าหลายรายการใน UI — รอหน้าจัดการหมวดหมู่ของ STEP 48)
- **ยังไม่มีการแจ้งเตือนลูกค้าเรื่องคูปองใกล้หมดอายุ** — `NotificationType.PROMOTION` มีใน enum
  แต่ยังไม่มีใครสร้างแถว และการประกาศถึงลูกค้าทุกคนยังทำไม่ได้ (กฎ STEP 24 ข้อ 1)
