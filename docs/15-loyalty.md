# 15 — Loyalty / Points (STEP 42)

> แต้มสะสม · ระดับสมาชิก · การใช้แต้มเป็นส่วนลด · และสิ่งที่ยังไม่ได้ทำ

```
/account/points               → แต้มคงเหลือ ระดับ ความคืบหน้า กติกา ประวัติแต้ม (ต้องล็อกอิน)
/checkout                     → ช่อง "ใช้แต้ม" — ส่วนลดคิดที่ server
/admin/customers              → คอลัมน์ "ระดับ · แต้ม" + ตัวกรองระดับ (กรองก่อนแบ่งหน้า)
/admin/customers/[userId]     → ระดับ · ประวัติแต้ม · ฟอร์มปรับแต้ม (loyalty:adjust)

GET  /api/users/me/loyalty                  แต้ม ระดับ ยอดที่ขาดถึงระดับถัดไป กติกาจาก config
GET  /api/users/me/loyalty/transactions     ประวัติแต้มของตัวเอง
GET  /api/checkout/summary?pointsToRedeem=  ยอดหลังใช้แต้ม (+ เหตุผลถ้าใช้ไม่ได้)
POST /api/orders { pointsToRedeem }         หักแต้มจริงในทรานแซกชันเดียวกับการสร้างคำสั่งซื้อ
GET  /api/admin/customers/:userId/points    ประวัติแต้มของลูกค้า (customer:read)
POST /api/admin/customers/:userId/points    ปรับแต้ม { delta, reason, idempotencyKey } (loyalty:adjust)
```

## จุดเริ่มต้น: คอลัมน์ที่ไม่มีใครเขียน

`User.points` · `User.loyaltyTier` · `User.totalSpent` มีอยู่ใน schema ตั้งแต่ STEP 2
แต่ **ไม่มีโค้ดไหนเขียนค่าเลย** — ทุกบัญชีเป็น "Member · 0 แต้ม · ยอดซื้อ 0" ตลอดกาล
(STEP 25 เลิกอ่าน `totalSpent` แล้วนับจากตาราง Order แทน · STEP 40 ซ่อนแต้มและระดับจากหน้าเว็บ)

STEP 42 แก้ด้วยการตัดสินใจคนละแบบกับแต่ละคอลัมน์:

| คอลัมน์            | ทำอะไร                                                     | เหตุผล                                                                                          |
| ------------------ | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `User.points`      | **เก็บไว้** เป็น cache ของสมุดแต้ม เขียนคู่กันในทรานแซกชัน | ต้องมีแถวให้ล็อกตอนหักแต้มแบบ atomic + มี CHECK `points >= 0` เป็นด่านสุดท้ายอยู่แล้ว           |
| `User.loyaltyTier` | **ถอดออก** — ระดับคำนวณสดจากยอดที่จ่ายจริง                 | cache ของระดับค้างค่าเก่าทันทีที่เกณฑ์ใน config เปลี่ยน โดยไม่มีอะไรฟ้อง                        |
| `User.totalSpent`  | **ถอดออก** — ยอดสะสมนับจากตาราง Order ทุกครั้ง             | หลังบ้านนับจาก Order อยู่แล้วตั้งแต่ STEP 25 · สองแหล่งความจริงของตัวเลขเดียวกันคือที่มาของบั๊ก |

(แพตเทิร์นเดียวกับสถานะคูปองของ STEP 41 และสถานะเตือนสต็อกของ STEP 16: **คำนวณสด ไม่เก็บเป็นคอลัมน์**)

## สมุดแต้ม `PointTransaction` — append-only

| ชนิด            | delta | เกิดเมื่อ                                                     | idempotencyKey             |
| --------------- | :---: | ------------------------------------------------------------- | -------------------------- |
| `EARN`          |   +   | ร้านได้รับเงิน — Stripe webhook ยืนยัน · COD ตอนกด "ส่งถึง"   | `order:<id>:earn`          |
| `REDEEM`        |   −   | สร้างคำสั่งซื้อที่ใช้แต้มเป็นส่วนลด                           | `order:<id>:redeem`        |
| `REDEEM_REFUND` |   +   | คำสั่งซื้อที่ใช้แต้มถูกยกเลิก (ทุกเส้นทาง)                    | `order:<id>:redeem-refund` |
| `EARN_REVERSAL` |  −/0  | คำสั่งซื้อที่ได้แต้มไปแล้วถูกยกเลิก (หักได้ไม่เกินยอดคงเหลือ) | `order:<id>:earn-reversal` |
| `ADJUSTMENT`    |   ±   | ร้านปรับให้ — ต้องมีเหตุผล + ผู้ทำรายการ + AdminLog           | `adjust:<uuid จากฟอร์ม>`   |

**ตัวเขียนมีตัวเดียว: `postPointTransaction()`** ใน [loyalty.service.ts](../backend/src/services/loyalty.service.ts)

```sql
UPDATE "User" SET "points" = "points" + $delta, "updatedAt" = now()
 WHERE "id" = $userId AND "points" + $delta >= 0
RETURNING "points" AS "after"
```

ไม่มีแถวกลับมา → แต้มไม่พอ → 409 → ทรานแซกชัน rollback (แพตเทิร์นเดียวกับการจองสต็อกของ STEP 10
และการปรับสต็อกของ STEP 15) · CHECK ของฐานข้อมูลที่ล็อกความถูกต้องไว้อีกชั้น:

- `PointTransaction_balance_math` — `balanceAfter = balanceBefore + delta`
- `PointTransaction_balances_non_negative` · `User_points_non_negative`
- `PointTransaction_delta_direction` — ทิศทางต้องตรงกับชนิด (EARN ห้ามติดลบ ฯลฯ)
- `Order_points_valid` — `pointsDiscount ≤ discountTotal` และแต้มกับมูลค่าเป็น 0 พร้อมกันเท่านั้น

### ⚠️ ลำดับของประวัติใช้ `sequence` ไม่ใช่ `createdAt`

ตอนยกเลิกคำสั่งซื้อ ระบบเขียน `REDEEM_REFUND` กับ `EARN_REVERSAL` ในทรานแซกชันเดียวกัน
— สองแถวได้ `createdAt` **เท่ากันเป๊ะ** เพราะ `CURRENT_TIMESTAMP` ของ PostgreSQL คือเวลาเริ่มทรานแซกชัน
และ uuid v7 ไม่รับประกันลำดับภายในมิลลิวินาทีเดียว → ประวัติอาจสลับบรรทัดจน "คงเหลือ" อ่านไม่ต่อกัน
(เจอตอนเขียนเทสต์ที่ไล่ตรวจ `balanceBefore` ต่อจาก `balanceAfter`) จึงเพิ่มคอลัมน์ `sequence` (SERIAL)
— ของผู้ใช้คนเดียวกันเขียนทีละรายการเสมอเพราะ `UPDATE "User"` ล็อกแถวไว้จน commit

## กฎที่ห้ามละเมิด

1. **ได้แต้มเมื่อร้านได้รับเงินจริงเท่านั้น** — Stripe: ตอน webhook ที่ลายเซ็นถูกต้อง ·
   COD: ตอนกด `DELIVERED` (จุดเดียวที่ตั้ง PAID ให้ COD — กฎ STEP 13 ข้อ 4) · **ไม่ใช่ตอนกดสั่งซื้อ**
   และไม่ใช่ตอนยืนยัน COD (เงินยังไม่ได้ — กฎ STEP 11 ข้อ 2)
2. **ฐานของแต้มคือ `Order.total`** — เงินที่จ่ายจริงทั้งบิล หลังหักคูปองและแต้มที่ใช้แล้ว
   จึงไม่มีการได้แต้มจากส่วนที่จ่ายด้วยแต้ม · คิดเป็น **สตางค์จำนวนเต็ม** ก่อนปัดลง
   (`199.7 + 0.1 + 0.2 = 199.99999999999997` ใน JS → หารตรง ๆ แล้วลูกค้าเสียไป 1 แต้ม · มีเทสต์จับกับดักนี้)
3. **ตัวคูณใช้ระดับ _ก่อน_ นับใบนี้** — ใบที่ทำให้ขึ้นระดับยังได้ตัวคูณของระดับเดิม
4. **ระดับคำนวณจาก "ยอดที่ได้รับ" ตัวเดียวกับที่หลังบ้านโชว์** (`PAID_ORDER_WHERE` ใน
   [order.model.ts](../backend/src/models/order.model.ts)) — แอดมินเห็นยอด 12,000 แต่ลูกค้าเป็น Silver ไม่ได้
   · ตัวกรองระดับในหลังบ้านใช้ SQL `HAVING SUM(total)` ซึ่ง **มีเทสต์เทียบกับ `PAID_ORDER_WHERE` ตรง ๆ**
5. **client ส่งได้แค่ `pointsToRedeem` (จำนวนแต้ม)** — มูลค่าเป็นบาท แต้มคงเหลือ เพดานของบิล
   คิดที่ server ทั้งหมด (มีเทสต์ยิง `pointsDiscount: 99999` + `total: 1` แล้วยืนยันว่าถูกเมิน)
6. **ส่วนลดจากแต้มถูกยุบลง `discountTotal`** — สูตรบิลยังเป็น `total = subtotal − discountTotal + shippingFee`
   (กฎ STEP 41 ข้อ 8: ห้ามเพิ่มช่องส่วนลดที่สอง) · `Order.pointsDiscount` บอกแค่ว่าส่วนลดก้อนไหนมาจากแต้ม
   · รายงานของ STEP 26 ที่รวม `discountTotal` จึงรวมส่วนลดจากแต้มด้วยโดยอัตโนมัติ
7. **แต้มคิดหลังคูปองเสมอ** — เพดาน = min(แต้มที่มี, 50% ของยอดสินค้า, ยอดสินค้าที่เหลือหลังหักคูปอง)
   เพราะ CHECK `Order_discount_not_over_subtotal` บังคับให้ส่วนลดทุกก้อนรวมกันไม่เกินยอดสินค้า
8. **ใช้ไม่ได้ต้องปฏิเสธพร้อมเหตุผล ไม่ปรับลดให้เงียบ ๆ** — 5 เหตุผลเป็นภาษาไทย
   (ไม่ใช่ทวีคูณ · ต่ำกว่าขั้นต่ำ · แต้มไม่พอ · บิลนี้ใช้ไม่ได้ · เกินเพดาน) · ถ้าหน้าเว็บโชว์ลด 50 บาท
   แล้ว server ตัดเหลือ 40 เอง ลูกค้าจะถูกเก็บเงินมากกว่าที่เห็น
9. **ยกเลิกคำสั่งซื้อทุกเส้นทางเรียก `releasePointsForCancelledOrder()`** คู่กับการคืนโควตาคูปอง
   (ลูกค้ายกเลิก · ร้านยกเลิก · หมดเวลาชำระเงิน · Stripe แจ้งว่าจ่ายไม่สำเร็จ/หมดเวลา)
   — คืนแต้มที่ใช้ก่อน แล้วค่อยหักแต้มที่ได้ (ใบเดียวกันที่ทั้งใช้และได้แต้ม แต้มที่คืนจะช่วยให้หักได้ครบ)
10. **แต้มที่ได้ถูกใช้ไปแล้ว → หักได้เท่าที่มี และบันทึกตรง ๆ ว่าขาดเท่าไร** — การยกเลิกต้องไม่ล้ม
    (ร้านต้องยกเลิกคำสั่งซื้อได้เสมอ) · แถว `EARN_REVERSAL` ที่ delta = 0 ได้รับอนุญาตโดยเจตนาเพื่อบันทึกว่า "พยายามหักแล้ว"
11. **`loyalty:adjust` = ADMIN ขึ้นไป** · ปรับแต้มตัวเองไม่ได้ (400) · แตะได้แค่บัญชีที่บทบาทต่ำกว่า (403)
    — ใช้ด่าน `assertCanManage()` ตัวเดียวกับการระงับบัญชีของ STEP 25 · **ต้องกรอกเหตุผล ซึ่งลูกค้าเห็น**
    ทั้งในประวัติแต้มและการแจ้งเตือน (ฟอร์มบอกไว้ตรง ๆ) · ไม่มีช่อง "ตั้งยอดคงเหลือ" มีแค่เพิ่ม/หักเท่าไร
12. **แจ้งเตือนเฉพาะที่ลูกค้ารู้สึกได้** — แต้มที่ได้แจ้ง **รวมไปใน "ชำระเงินสำเร็จ"** ไม่แยกเป็นรายการใหม่
    (COD ตอนส่งถึงมี 2 รายการอยู่แล้ว) · ขึ้นระดับแจ้งครั้งเดียวต่อระดับ · ร้านปรับแต้มแจ้งทุกครั้งพร้อมเหตุผล
    · ใช้ type ใหม่ `LOYALTY_UPDATE` (ความหมายต้องอยู่ใน enum ที่ query ได้ — บทเรียน STEP 24)
13. **แต้มและระดับไม่อยู่ใน session ของ Auth.js อีกแล้ว** — อ่านจาก `/api/users/me/loyalty` ที่เดียว
    (เดิม callback `session` อ่านคอลัมน์ที่ไม่มีใครเขียนมาใส่ทุกคำขอ)

## ยืนยันกับแอปจริงแล้ว

สร้างลูกค้าทดสอบชั่วคราวแล้วเดินผ่าน API จริงทั้งหมดบน dev server (ไม่ได้เขียนฐานข้อมูลตรง):
สั่งซื้อ ฿920 แบบ COD → ร้านกดส่งถึง → **ได้ 92 แต้ม** → ร้านเติม 500 แต้มผ่าน `POST /api/admin/customers/:id/points`
→ สั่งใบใหม่ใช้แต้มสูงสุดที่ server ยอม **590 แต้ม = ลด 59 บาท** (ยอดสินค้า 290 − 59 + ค่าส่ง 50 = 281)
→ ยอดคงเหลือ 2 แต้ม **= ผลรวมของสมุดแต้ม** · จากนั้นรันตัวตรวจในเบราว์เซอร์จริงด้วยบัญชีนี้แล้วลบข้อมูลทิ้งทั้งหมด

- `audit-chrome` **49 หน้า 0 ปัญหา** — รวม `/account/points` · `/checkout` (ทั้งแบบแต้มไม่พอและแบบมีช่องกรอก) ·
  `/account/orders/[n]` · `/admin/customers/[id]`
- `audit-responsive` **147 หน้า-ความกว้าง 0 ปัญหา** (360 · 768 · 1280)
- ⚠️ ระหว่างนี้เจอว่าตัวตรวจ **ไม่เคยเปิดหน้ารายละเอียดในหลังบ้านเลย** (อ่าน key ผิดจาก API รายการ)
  — แก้แล้วเจอ checkbox ขนาด 20px ที่หน้าแก้สินค้าซึ่งซ่อนอยู่หลังบั๊กนี้มาตลอด (แก้แล้วเช่นกัน)

  แถวแรกแทนการล้างทิ้งเงียบ ๆ — ยอดจึงยังอธิบายได้ด้วยสมุดแต้ม
- `20261006130000_add_point_transaction_sequence` — คอลัมน์ `sequence` (ดูหัวข้อด้านบน)
- **สิทธิ์ `loyalty:adjust` มาจาก seed** — environment ที่ deploy แล้วต้องรัน `npm run db:seed` ซ้ำ
  ไม่งั้น ADMIN จะปรับแต้มไม่ได้ (ได้ 403 — ล้มแบบปลอดภัย ไม่ใช่เปิดช่อง)

## ที่ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **แต้มไม่มีวันหมดอายุ และระดับไม่ลดตามเวลา** — ทั้งสองต้องมี job ตามเวลาและการแจ้งเตือนล่วงหน้า
  (STEP 52) · หน้า `/account/points` บอกเรื่องนี้ไว้แล้ว
- **ไม่ให้แต้มย้อนหลังกับคำสั่งซื้อที่จ่ายก่อนเปิดระบบ** — ระดับนับยอดเก่าด้วย (คิดจากตาราง Order)
  แต่แต้มเริ่มนับตั้งแต่ STEP 42 · การให้ย้อนหลังต้องตัดสินใจทางธุรกิจก่อน ไม่ใช่ใส่ใน migration เงียบ ๆ
- **แต้มเข้าทันทีที่ได้เงิน ยังไม่มี "แต้มรอยืนยัน"** — ถ้าคำสั่งซื้อที่จ่ายแล้วถูกยกเลิกหลังลูกค้า
  ใช้แต้มไปแล้ว ร้านจะหักคืนได้ไม่ครบ (บันทึกส่วนที่ขาดไว้ในประวัติ) · การกันเรื่องนี้ต้องมีช่วงรอ
  ตามนโยบายคืนสินค้า (STEP 43) และ job ปล่อยแต้ม (STEP 52)
- **ยังไม่ใช้กับการคืนเงิน (`REFUNDED`)** — ระบบคืนเงินคือ STEP 43 ซึ่งต้องเรียก
  `releasePointsForCancelledOrder()` ด้วย (ฟังก์ชันรองรับแล้ว แต่ยังไม่มีเส้นทางคืนเงินให้เรียก)
- **AI Customer Service ยังตอบเรื่องแต้มไม่ได้** — ไม่มีบทความในคลังความรู้ (ต้องประกอบตัวเลขจาก
  config ตามกฎ STEP 21 ข้อ 1) · ถามมาตอนนี้ AI จะตอบว่าไม่พบข้อมูลแล้วแนะนำให้ติดต่อเจ้าหน้าที่
- **ตัวกรองระดับในหลังบ้านส่งรายการ id ไปกับ `IN`/`NOT IN`** — เร็วพอที่ลูกค้าหลักพัน
  ถ้าโตถึงหลักแสนควรเขียนคิวรีรายการลูกค้าทั้งก้อนเป็น SQL ที่ join ยอดรวมเอง
