# 16 — Return / Refund (STEP 43)

> คำขอคืนสินค้า · การตรวจรับของ · การบันทึกคืนเงิน · ผลต่อสต็อก แต้ม และรายงาน · และสิ่งที่ยังไม่ได้ทำ

```
/account/orders/[orderNumber]          → ส่วน "คืนสินค้า" (ใบที่ส่งถึงแล้ว) + แถว "ร้านคืนเงินแล้ว"
/account/orders/[orderNumber]/return   → ฟอร์มขอคืน: เลือกชิ้น · จำนวน · เหตุผล · รายละเอียด (ต้องล็อกอิน)
/account/returns                       → คำขอคืนของฉันทุกสถานะ · ยอดที่จะได้คืน · ยกเลิกคำขอ
/admin/returns                         → คิวคำขอคืน + ใบที่ร้านยกเลิกหลังลูกค้าจ่ายแล้วแต่ยังไม่ได้คืนเงิน (order:read)
/admin/returns/[returnId]              → อนุมัติ/ไม่รับคืน · ตรวจรับของ · บันทึกคืนเงิน
/admin/orders/[orderNumber]            → ส่วน "คืนเงิน" ของใบที่ร้านยกเลิกหลังลูกค้าจ่ายแล้ว (order:refund)

GET   /api/returns                              คำขอของตัวเอง
GET   /api/returns/eligibility/:orderNumber     ขอได้ไหม · วันสุดท้าย · ชิ้นไหนคืนได้อีกกี่ชิ้น
POST  /api/returns                              { orderNumber, reason, detail, items, idempotencyKey }
POST  /api/returns/:returnId/cancel             ลูกค้ายกเลิกเอง (ได้จนกว่าร้านจะรับของ)
GET   /api/admin/returns · /api/admin/returns/:returnId                  (order:read)
PATCH /api/admin/returns/:returnId/status   { status, note }             (order:update)
POST  /api/admin/returns/:returnId/receive  { items: [{ returnItemId, restock }] }   (order:update)
POST  /api/admin/returns/:returnId/refund   { method, reference, note?, idempotencyKey }   (order:refund)
POST  /api/admin/orders/:orderNumber/refund { method, reference, note?, idempotencyKey }   (order:refund)
```

## จุดเริ่มต้น: เงินที่ออกจากร้านโดยไม่มีที่บันทึก

ก่อน STEP นี้ enum มี `OrderStatus.REFUNDED` · `PaymentStatus.REFUNDED` · `Order.refundedAt` ·
`Payment.refundAmount` อยู่แล้ว **แต่ไม่มีเส้นทางไหนเขียนเลย** และมีสองช่องว่างที่ร้ายกว่านั้น:

1. **บทความนโยบายในคลังความรู้บอกลูกค้าว่า "ยื่นคำขอคืนเงินเองบนเว็บไม่ได้"** — ซึ่ง AI Customer Service
   หยิบไปตอบในฐานะนโยบายร้าน · พอ STEP นี้เปิดให้ยื่นเองได้ ข้อความเดิมจะกลายเป็นเท็จทันที
   → migration `20261007091000_update_returns_policy_article` แทนที่ **เฉพาะย่อหน้านั้น** และเฉพาะเมื่อยังเป็น
   ข้อความเดิมอยู่ (ถ้าแอดมินแก้บทความไปแล้ว `WHERE position(…) > 0` ไม่ match แล้วไม่แตะของเขา)
   เพราะบทความอยู่ในฐานข้อมูลและ seed ใส่ครั้งเดียว (STEP 21) — แก้ข้อความใน source อย่างเดียวไม่ถึงฐานข้อมูลที่มีอยู่
2. **หลังบ้านยกเลิกใบที่ลูกค้าจ่ายแล้วได้มาตั้งแต่ STEP 13 แต่ไม่มีที่บันทึกว่าคืนเงินแล้ว**
   ใบพวกนี้ค้างเป็น "ยกเลิก + จ่ายแล้ว" ตลอดไป ไม่มีใครรู้ว่าเงินของลูกค้ากลับไปหรือยัง
   → ตอนนี้โผล่เป็นคิว "รอคืนเงิน" ที่ `/admin/returns` และบันทึกได้ที่หน้ารายละเอียดคำสั่งซื้อ

## ⚠️ ระบบไม่ได้โอนเงินเอง

`Refund` คือ **บันทึกว่าพนักงานคืนเงินไปแล้วจริง** (วิธีไหน · เลขอ้างอิงอะไร · ใครบันทึก) ไม่ใช่คำสั่งโอนเงิน
ยังไม่ได้ต่อ Stripe Refund API เพราะไม่มีบัญชี Stripe ให้ยืนยันกับของจริง —
adapter ที่ทดสอบกับของจริงไม่ได้แย่กว่าการบอกความจริง (กฎเดียวกับ Redis ของ STEP 34)
ฟอร์มบันทึกคืนเงินจึงเขียนตรง ๆ ว่า **"ระบบไม่ได้โอนเงินให้"** และไม่มีช่องกรอกยอดเงินเลย

| ลูกค้าจ่ายด้วย        | วิธีคืนที่บันทึกได้                                                                 |
| --------------------- | ----------------------------------------------------------------------------------- |
| Stripe                | `STRIPE_DASHBOARD` (คืนกลับช่องทางเดิม) หรือ `BANK_TRANSFER` (Stripe คืนไม่ได้แล้ว) |
| เก็บเงินปลายทาง (COD) | `BANK_TRANSFER` เท่านั้น — เงินสดอยู่ที่ร้าน                                        |

กติกาอยู่ที่ `refundMethodsFor()` ใน [config/returns.ts](../backend/src/config/returns.ts) · server ตรวจซ้ำตอนบันทึก

## เส้นทางของคำขอ

```
REQUESTED ──(ร้านอนุมัติ)──▶ APPROVED ──(ร้านตรวจรับของ)──▶ RECEIVED ──(แอดมินบันทึกคืนเงิน)──▶ REFUNDED
    │                           │
    ├──(ร้านไม่รับคืน + เหตุผล)──┴──▶ REJECTED
    └──(ลูกค้ายกเลิกเอง)─────────────▶ CANCELLED   ← ได้ทั้งตอน REQUESTED และ APPROVED
```

- **ขอคืนได้เมื่อ:** ใบเป็นของตัวเอง · `DELIVERED` · ร้านได้รับเงินแล้ว · ยังไม่เลย
  `RETURN_WINDOW_DAYS` (7 วัน) นับจาก `deliveredAt` ที่บันทึกจริง · ไม่มีคำขอที่ยังไม่จบค้างอยู่ ·
  ยังมีชิ้นที่ยังไม่ถูกขอคืน — ไม่ผ่านข้อไหนตอบเหตุผลข้อนั้น (ลำดับการตรวจ = สิ่งที่ลูกค้าแก้ได้ก่อน)
- **เหตุผลที่ขอคืนเงินได้มีแต่ความผิดของร้าน** (`DEFECTIVE` · `WRONG_ITEM`) ตามนโยบายเดิมของร้าน
  "เปลี่ยนใจ / ใส่ไม่พอดี" **ไม่อยู่ในรายการโดยเจตนา** — นโยบายร้านคือ "เปลี่ยนไซซ์" ซึ่งต้องส่งของชิ้นใหม่
  และยังไม่มีระบบรองรับ ฟอร์มจึงบอกให้ติดต่อฝ่ายบริการลูกค้าแทน
- **เลขคำขอ = เลขคำสั่งซื้อ + `-R<ลำดับ>`** (`TS-20261006-0001-R1`) — ไม่พิมพ์รูปแบบเลขคำสั่งซื้อซ้ำ
  (กฎ STEP 40 ข้อ 1) และมีเทสต์ยืนยันว่าตัวอ่านเลขคำสั่งซื้อของ AI ยังจับเลขคำสั่งซื้อจากมันได้

## เงินคืนเท่าไร — คิดที่ server เสมอ

กฎทั้งหมดอยู่ที่ [models/return.model.ts](../backend/src/models/return.model.ts) (ฟังก์ชันบริสุทธิ์) ·
คิดเป็น **สตางค์จำนวนเต็ม** (บทเรียนทศนิยมลอยของ STEP 42)

| ครั้งนี้                   | เงินที่คืน                                            |
| -------------------------- | ----------------------------------------------------- |
| คืนบางชิ้น                 | `floor(total × ยอดสินค้าที่คืน / subtotal)` ถึงสตางค์ |
| ทำให้ทุกชิ้นในบิลถูกคืนครบ | `total − refundedTotal` (เงินที่เหลือทั้งหมด)         |

- **ส่วนลดทุกก้อน (คูปอง · แต้ม) และค่าส่งถูกเฉลี่ยตามมูลค่าชิ้นนั้นเอง** — ไม่ต้องรู้ว่าคูปองเป็นชนิดไหน
  และไม่มีทางคืนเกินที่ลูกค้าจ่ายจริง
- **ครั้งสุดท้ายได้เศษทั้งหมด** — เศษสตางค์จากการปัดลงของครั้งก่อน ๆ และค่าส่งกลับไปหาลูกค้าครบ
  (เหตุผลที่คืนได้มีแต่ความผิดของร้าน ร้านจึงคืนค่าส่งด้วย) · ผลรวมทุกครั้ง = `total` พอดี
  (เทสต์สุ่ม 1,000 บิลที่แบ่งคืนหลายครั้งยืนยัน)
- **หน้าเว็บแสดงยอดที่จะได้คืนจากสูตรเดียวกับที่ใช้ตอนบันทึกจริง** (`estimatedRefund`) ไม่ใช่ตัวเลขประมาณ
- ลูกค้าส่งได้แค่ ชิ้น · จำนวน · เหตุผล · รายละเอียด · พนักงานส่งได้แค่ วิธี · เลขอ้างอิง ·
  ฟิลด์ยอดเงินที่แนบมาถูก Zod ตัดทิ้ง (มีเทสต์ยิง `amount` มาแล้วยืนยันว่าถูกเมิน)

## ความถูกต้องที่ฐานข้อมูลบังคับ

| ด่าน                                                                                                                              | กันอะไร                                                                    |
| --------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `UPDATE "Order" SET "refundedTotal" = … WHERE "refundedTotal" + $amount::numeric(12,2) <= "total"`                                | สองคนกดคืนเงินพร้อมกันแล้วคืนเกินที่ลูกค้าจ่าย                             |
| CHECK `Order_refunded_valid` (`0 ≤ refundedTotal ≤ total`)                                                                        | ด่านสุดท้ายถ้าโค้ดอื่นเขียนพลาด                                            |
| partial unique `ReturnRequest_one_open_per_order` (REQUESTED/APPROVED/RECEIVED)                                                   | สองคำขอพร้อมกันของบิลเดียว (คู่กับ `SELECT … FOR UPDATE` ของแถวคำสั่งซื้อ) |
| `Refund.returnRequestId` unique · `idempotencyKey` unique ทั้ง `ReturnRequest` และ `Refund`                                       | กดซ้ำแล้วคืนเงิน/ยื่นคำขอซ้ำ                                               |
| ทุกการเปลี่ยนสถานะ `updateMany … where status = เดิม`                                                                             | สองพนักงานกดพร้อมกัน → คนที่สองได้ 409 ไม่ใช่ทำซ้ำ                         |
| CHECK `ReturnItem_quantity_positive` · `Refund_amount_positive` · `Refund_reference_not_blank` · `ReturnRequest_detail_not_blank` | ข้อมูลว่าง/ศูนย์ที่ไม่มีความหมาย                                           |

⚠️ **`::numeric(12,2)` จำเป็น** — ปล่อยให้พารามิเตอร์เป็น float แล้ว `281.55` กลายเป็น
`281.55000000000001` ตอนเทียบกับคอลัมน์ numeric แล้วถูกปฏิเสธทั้งที่ยอดถูกต้อง

## สต็อก — พนักงานตัดสินทีละชิ้นตอนตรวจรับ

- **ต้องระบุผลของทุกชิ้น** (รับเข้าคลัง / ไม่รับ) — ไม่มีค่าเริ่มต้นให้ลืมกด แล้วของชำรุดกลับไปขายต่อ
- ขายต่อได้ → `restockReturnedItem()` เขียน movement `RETURN` (`referenceType = 'RETURN_REQUEST'` ·
  key `return:<id>:restock:<itemId>`) + `Product.totalStock` ในทรานแซกชันเดียวกัน (กฎ STEP 15 ข้อ 1)
  แล้วตรวจเตือนสต็อกหลัง commit (กฎ STEP 16 ข้อ 7)
- ชำรุด → ไม่แตะคลัง เพราะของถูกตัดออกจากคลังไปแล้วตั้งแต่ตอนขาย

## แต้ม — สัดส่วนเดียวกับเงิน

ตอนบันทึกคืนเงิน `settlePointsForReturn()` คืนแต้มที่ลูกค้าใช้กับบิลนั้น + หักแต้มที่ได้จากบิลนั้น
ตามสัดส่วนเดียวกับเงิน (ครั้งสุดท้ายได้ส่วนที่เหลือ) ในทรานแซกชันเดียวกับ `Refund`

- ใช้ตัวกลาง `movePointsBack()` ตัวเดียวกับการยกเลิกคำสั่งซื้อ (STEP 42) ซึ่งอ่านยอดจากสมุดแต้มของบิลนั้นทุกครั้ง
  → **ไม่มีทางคืนเกินที่ใช้ หรือหักเกินที่ได้** แม้บิลเดียวกันจะผ่านทั้งการคืนบางชิ้นและการยกเลิก
- แต้มที่ได้ถูกใช้ไปแล้ว → หักได้ไม่เกินยอดคงเหลือ แล้วบันทึกตรง ๆ ว่าขาดเท่าไร (การคืนเงินต้องไม่ล้ม)
- `releasePointsForCancelledOrder()` เปลี่ยนมาใช้ `movePointsBack()` ด้วย (คิดจากยอดที่เหลือ ไม่ใช่ยอดเต็ม)

## รายงานและยอดซื้อ — หัก `refundedTotal` ทุกที่

`Order.refundedTotal` เป็น cache ที่เขียนในทรานแซกชันเดียวกับแถว `Refund` เสมอ
(เทสต์ตรวจว่า = ผลรวมของ `Refund` ทุกบิล) · ทุกตัวเลข "เงินที่ร้านได้รับ" ใช้ยอดสุทธิ:

| ที่                                              | เดิม             | ตอนนี้                                             |
| ------------------------------------------------ | ---------------- | -------------------------------------------------- |
| ภาพรวมร้าน `/admin` (ยอดขายวันนี้/เดือนนี้)      | `SUM(total)`     | `SUM(total − refundedTotal)` (`netPaid`)           |
| `/admin/analytics` กราฟ · KPI · ลูกค้า · วิธีส่ง | `SUM(total)`     | `NET_PAID_SQL` + แถว **"คืนเงิน"** ในตารางกระทบยอด |
| แยกตามช่องทางจ่าย                                | `Payment.amount` | `amount − refundAmount`                            |
| ยอดซื้อของลูกค้าในหลังบ้าน + ตัวกรองยอดซื้อ      | `SUM(total)`     | `SUM(total − refundedTotal)`                       |
| ระดับสมาชิก (`lifetimeSpendOf`)                  | `SUM(total)`     | `SUM(total) − SUM(refundedTotal)`                  |

⚠️ **ยอดตามสินค้า/หมวด (`OrderItem.lineTotal`) ยังไม่หักการคืนบางชิ้น** — หน้ารายงานเขียนกำกับไว้แล้ว
(การหักต้องรู้ว่าเงินคืนก้อนไหนเป็นของชิ้นไหน ซึ่งสูตรตามสัดส่วนไม่ได้แยกไว้ระดับรายการ)

## ใบที่ร้านยกเลิกหลังลูกค้าจ่ายแล้ว

`adminRefundCancelledOrder()` — ใช้ได้เฉพาะ `CANCELLED` + `paymentStatus = PAID` · คืน **ยอดที่เหลือทั้งหมด** ·
ตั้ง `paymentStatus = REFUNDED` แต่ **สถานะคำสั่งซื้อยังเป็น `CANCELLED`** (เรื่องที่เกิดคือยกเลิก ไม่ใช่คืนสินค้า)
· สต็อกและแต้มถูกจัดการไปแล้วตอนยกเลิก ที่นี่จึงบันทึกเฉพาะเรื่องเงิน · AdminLog `order.refund`
· ไทม์ไลน์ของลูกค้าแสดงทั้ง "ยกเลิก" และ "คืนเงินแล้ว" ตาม timestamp ที่บันทึกจริง

## สิทธิ์

| ทำอะไร                                        | สิทธิ์         | ใครมีตาม seed   |
| --------------------------------------------- | -------------- | --------------- |
| ดูคิว/รายละเอียดคำขอ                          | `order:read`   | EMPLOYEE ขึ้นไป |

คนที่แพ็กของและตรวจรับของคืนได้ ไม่ควรเป็นคนบันทึกว่าเงินออกจากร้านได้ด้วย
(แพตเทิร์นเดียวกับ STEP 17 ข้อ 8 · STEP 25 ข้อ 12) · มีเทสต์ยืนยันว่า EMPLOYEE ได้ 403
· สิทธิ์ทั้งสามมีใน seed อยู่แล้ว **ไม่ต้องรัน seed ซ้ำ**

## การแจ้งเตือนและ AdminLog

- `NotificationType.RETURN_UPDATE` ใหม่ (หมวดคำสั่งซื้อ) — แจ้งเมื่อ อนุมัติ · ไม่รับคืน (พร้อมเหตุผลของร้าน) ·
  ร้านได้รับของ · คืนเงินแล้ว · และเมื่อร้านคืนเงินใบที่ยกเลิก · ผ่าน `notifyOnce` + `notifySafely` หลัง commit
  · ลิงก์ไป `/account/returns` (หรือหน้าคำสั่งซื้อเมื่อไม่มีเลขคำขอ)
- AdminLog: `return.approve` · `return.reject` · `return.receive` · `return.refund` · `order.refund`
  · `targetType = 'ReturnRequest'` ลิงก์ไป `/admin/returns/<id>` · หมวดตัวกรอง "คืนสินค้า" ใหม่
  (และ "คูปอง" ที่ STEP 41 เขียน log ไว้แต่ไม่มีหมวดให้กรอง)

  — FK ไปคำสั่งซื้อ/ผู้ใช้เป็น `Restrict` (ประวัติเงินห้ามหายตามการลบ) · ผู้บันทึกเป็น `SetNull` (กฎ STEP 27 ข้อ 3)
- partial unique index และ CHECK 5 ตัวตามตารางด้านบน

## ที่ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ยังไม่โอนเงินอัตโนมัติ** — ไม่มี Stripe Refund API (ดูด้านบน) · ระบบบันทึกสิ่งที่พนักงานทำไปแล้วเท่านั้น
- **ยังไม่มีการเปลี่ยนไซซ์/เปลี่ยนสินค้า** — ต้องสร้างการส่งของชิ้นใหม่ (คำสั่งซื้อใหม่ · ค่าส่ง · สต็อก)
  ยังไม่มี STEP ไหนรับงานนี้ไว้ · ระหว่างนี้ลูกค้าติดต่อฝ่ายบริการลูกค้า (ฟอร์มบอกไว้แล้ว)
- **ลูกค้าแนบรูปสินค้าที่มีตำหนิไม่ได้** — ระบบอัปโหลดมีแล้วตั้งแต่ STEP 47 (รูปสินค้า · รูปรีวิว)
  แต่ยังไม่ได้ต่อเข้ากับคำขอคืน · ยังไม่มี STEP ไหนรับงานนี้ไว้ · ถ้าทำ ต้องผ่าน `storeImage()`
  และเพิ่มขาของตารางคำขอคืนใน `usedMediaUrlsSql()` · ห้ามแก้ด้วยการรับ URL จาก client
- **ยังไม่มีป้ายส่งของคืนหรือเลขพัสดุขากลับ** — ร้านแจ้งวิธีส่งคืนผ่านข้อความถึงลูกค้า (`staffNote`)
  · ระบบพัสดุของ STEP 44 รองรับเฉพาะขาส่งออก — พัสดุขากลับของการคืนสินค้ายังไม่มี STEP ไหนรับงานนี้ไว้
- **คำขอที่อนุมัติแล้วแต่ลูกค้าไม่ส่งของกลับ ไม่หมดอายุเอง** — ร้านปิดด้วย "ไม่รับคืน" พร้อมเหตุผลได้
  · การปิดอัตโนมัติต้องมี job ตามเวลา (STEP 52)
- **COD คืนด้วยการโอน แต่ระบบไม่เก็บเลขบัญชีลูกค้า** โดยเจตนา (ข้อมูลการเงิน + PDPA ของ STEP 53)
  · เจ้าหน้าที่ขอผ่านแชตฝ่ายบริการลูกค้า ตามที่บทความนโยบายเขียนไว้
- **ยอดตามสินค้า/หมวดในรายงานยังไม่หักการคืนบางชิ้น** (ดูหัวข้อรายงาน)
- **ยังไม่มีอีเมลแจ้งผล** — แจ้งในแอปเท่านั้น (STEP 50)
