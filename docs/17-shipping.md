# 17 — Shipping Management (STEP 44)

> อัตราค่าส่งที่ร้านแก้เองได้ · บทความนโยบายที่ใช้ค่าสด · พัสดุ (ส่งไม่สำเร็จ · ตีกลับ · ส่งใหม่) · และสิ่งที่ยังไม่ได้ทำ

```
/admin/shipping                 → อัตราค่าส่งทุกวิธี (ดู = shipment:read · แก้ = settings:manage)
/admin/shipments                → พัสดุทั้งร้าน + จำนวนต่อสถานะ + "เลยกำหนดส่ง" (shipment:read)
/admin/shipments/[shipmentId]   → ประวัติสถานะ · เปลี่ยนสถานะ · แก้เลขที่กรอกผิด · ส่งใหม่ (shipment:update)
/admin/orders/[orderNumber]     → รายการพัสดุพร้อมประวัติ + ฟอร์ม "ส่งพัสดุใหม่" เมื่อพัสดุตีกลับ
/account/orders/[orderNumber]   → ลูกค้าเห็นสถานะพัสดุ ประวัติ และเหตุผลที่ร้านบันทึกไว้
/checkout                       → ยอดส่งฟรีของแต่ละวิธี · ยอดที่เห็นต้องเท่ากับยอดที่เก็บ (expectedTotal)
/  (หน้าแรก)                    → "ส่งฟรีเมื่อยอดสินค้าครบ …" อ่านจากอัตราจริง

GET   /api/shipping/options                         วิธีที่เปิดใช้ + freeShippingFrom (สาธารณะ)
GET   /api/admin/shipping/rates                     (shipment:read)
PATCH /api/admin/shipping/rates/:method             (settings:manage)
GET   /api/admin/shipments?status=&overdue=&q=      (shipment:read)
GET   /api/admin/shipments/:shipmentId              (shipment:read)
PATCH /api/admin/shipments/:shipmentId/status       { status, note? }          (shipment:update)
PATCH /api/admin/shipments/:shipmentId              { carrier?, trackingNumber?, trackingUrl?, estimatedDelivery?, reason }
POST  /api/admin/orders/:orderNumber/shipments      { carrier, trackingNumber, trackingUrl?, estimatedDelivery? }
```

## จุดเริ่มต้น

1. **ค่าส่งเป็นค่าคงที่ใน `config/shipping.ts`** — ร้านแก้เองไม่ได้ ต้องแก้โค้ดแล้ว deploy
   (CLAUDE.md STEP 10 ข้อ 6 จดไว้ว่า STEP 44 จะย้ายไปฐานข้อมูล)
2. **แถว `Shipment` ถูกสร้างตอนกด "จัดส่งแล้ว" แล้วไม่มีใครแตะอีก** — ส่งไม่สำเร็จ · ตีกลับ · กรอกเลขผิด ·
   ต้องส่งใหม่ ไม่มีที่บันทึกเลย และ **ใบที่พัสดุตีกลับยกเลิกไม่ได้** (ไม่มีเส้นทาง SHIPPING → CANCELLED)
   ของจึงค้างในระบบว่า "กำลังส่ง" ตลอดไปทั้งที่วางอยู่ในร้าน — งานที่เกิดทุกวันกับร้านที่มี COD
3. **หน้าแรกโฆษณา "ส่งฟรี เมื่อสั่งครบ 690.-"** ซึ่งคือเงื่อนไขของ **คูปอง** FREESHIP690 (ต้องกรอกรหัส
   มีวันหมดอายุ) ไม่ใช่ส่งฟรีอัตโนมัติ — ส่งฟรีจริงคือ 1,000 บาท ลูกค้าที่สั่ง 700 บาทโดยไม่ใส่รหัสโดนค่าส่ง

## อัตราค่าส่ง — ข้อมูลในตาราง `ShippingRate`

- หนึ่งแถวต่อหนึ่งวิธี (enum `ShippingMethod`) · migration ใส่ค่าเดิมของ config ทุกตัว
  **ยอดที่เก็บจึงเท่าเดิมทุกบาทหลัง deploy** · ร้านแก้ได้: ค่าส่ง · ยอดส่งฟรี (ว่าง = ไม่มีโปร) ·
  ระยะเวลา · คำอธิบาย · จังหวัดที่ให้บริการ · เปิด/ปิด
- **ชื่อวิธีแก้ไม่ได้** — อยู่ใน `SHIPPING_METHOD_NAME` ของ config เพราะคำสั่งซื้อทุกใบอ้าง enum นี้
  ถ้าแก้ชื่อได้ "ส่งธรรมดา" ในประวัติคำสั่งซื้อเก่าจะกลายเป็นชื่ออื่นตาม
- **ระยะเวลาที่บอกตอนสั่งเก็บเป็น snapshot** (`Order.shippingEtaText`) — ร้านแก้ข้อความภายหลัง
  ประวัติต้องบอกสิ่งที่ลูกค้าเห็นตอนกดสั่ง (กฎ STEP 10 ข้อ 5) · ใบเก่าเติมค่าจากข้อความเดิมใน migration
  (ข้อความเหล่านั้นไม่เคยเปลี่ยนก่อน STEP นี้)
- **ทุกที่ที่คิดค่าส่งอ่านจากตารางเดียวกัน**: สรุปยอด checkout · การสร้างคำสั่งซื้อ (อ่านในทรานแซกชัน) ·
  คูปองส่งฟรี · บทความคลังความรู้ · AI Customer Service · `/api/shipping/options`
- **เทียบยอดส่งฟรีเป็นสตางค์** (`0.7 + 0.1 < 0.8` ใน JS — บทเรียน STEP 42)

### ด่านของการแก้อัตรา

| ด่าน                                                            | กันอะไร                                                                                  |
| --------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| **ปิดวิธีสุดท้ายที่เปิดอยู่ไม่ได้** (ล็อกทุกแถวก่อนนับ)         | ไม่เหลือวิธีจัดส่ง = ทั้งร้านสั่งซื้อไม่ได้ · สองแอดมินปิดคนละวิธีพร้อมกันแล้วเหลือศูนย์ |
| **คำอธิบายห้ามมีจำนวนเงิน** (`… บาท` / `฿`)                     | ตัวเลขในคำอธิบายค้างค่าเก่าทันทีที่แก้ค่าส่ง แล้วไปโผล่ในบทความที่ AI ใช้ตอบลูกค้า       |
| **จังหวัดต้องเป็นชื่อในรายการ 77 จังหวัด** (`THAI_PROVINCES`)   | การเทียบเป็นข้อความตรงตัว — พิมพ์ "กรุงเทพฯ" แล้วไม่มีลูกค้าคนไหนเลือกวิธีนั้นได้เลย     |
| ทศนิยมไม่เกิน 2 ตำแหน่ง · ยอดส่งฟรีต้อง > 0 · CHECK ในฐานข้อมูล | ค่าที่เก็บลงคอลัมน์ไม่ได้ / ยอดส่งฟรี 0 ที่แปลว่า "ส่งฟรีทุกใบ" โดยไม่ตั้งใจ             |
| แก้ = `settings:manage` (ADMIN ขึ้นไป) · ดู = `shipment:read`   | ค่าส่งคือเงินที่เก็บจากลูกค้าทุกคน · พนักงานต้องตอบเรื่องค่าส่งได้                       |
| AdminLog `shipping.rate.update` before/after คีย์ชุดเดียวกัน    | ตรวจย้อนหลังได้ว่าใครแก้ค่าส่งจากเท่าไรเป็นเท่าไร (กฎ STEP 27)                           |

### ⚠️ ยอดที่เห็นต้องเท่ากับยอดที่เก็บ — `expectedTotal`

พอค่าส่งแก้ได้ระหว่างที่ลูกค้าเปิดหน้า checkout ค้างไว้ ยอดที่เขาเห็นอาจไม่ใช่ยอดที่ระบบจะเก็บ
(ราคาสินค้าและคูปองก็เปลี่ยนได้แบบเดียวกันมาตั้งแต่ก่อน STEP นี้) → หน้า checkout ส่งยอดที่ **แสดงอยู่** มาด้วย
server **ใช้เทียบเท่านั้น ไม่ใช้คิดเงิน** (ยอดจริงยังคิดจากฐานข้อมูลทั้งหมด) · ไม่ตรง → **409**
พร้อม `details: [{ field: 'expectedTotal' }]` · ไม่สร้างคำสั่งซื้อ ไม่จองของ · หน้าเว็บโหลดยอดใหม่ ตรวจคูปองใหม่
ล้างแต้ม แล้วให้ลูกค้ากดยืนยันอีกครั้ง (ไม่บังคับส่งเพื่อให้ผู้เรียกเดิมยังใช้ได้)

## บทความนโยบาย — ตัวแปรที่แทนค่าตอนอ่าน

บทความอยู่ในฐานข้อมูลและแอดมินแก้ได้ (STEP 21) — ถ้ายังเก็บตัวเลขค่าส่งเป็นข้อความตายตัว
**การแก้ค่าส่งครั้งแรกจะทำให้ AI สัญญากับลูกค้าคนละอย่างกับที่ระบบเก็บเงิน** (กฎกลางข้อ 3)

→ บทความเก็บ **ตัวแปร** แล้ว backend แทนค่าจากตาราง `ShippingRate` **ทุกครั้งที่มีคนอ่าน**
([models/policy-tokens.ts](../backend/src/models/policy-tokens.ts))

| ตัวแปร                 | กลายเป็น                                                               |
| ---------------------- | ---------------------------------------------------------------------- |
| `{{shipping.rates}}`   | ตารางค่าส่งทุกวิธีที่เปิดใช้ (ค่าส่ง · ยอดส่งฟรี · ระยะเวลา · พื้นที่) |
| `{{shipping.free}}`    | ประโยคเงื่อนไขส่งฟรี — **ไม่มีโปรต้องบอกว่าไม่มี** ไม่ใช่ "ครบ 0 บาท"  |
| `{{shipping.eta}}`     | ระยะเวลาของทุกวิธีในบรรทัดเดียว                                        |
| `{{shipping.methods}}` | รายชื่อวิธีที่เลือกได้                                                 |

- แทนค่าใน **ทุกเส้นทางที่คนอ่าน**: `/faq` · ค้นหา · คำตอบของ AI (`/ask`) · และให้คะแนนความเกี่ยวข้องกับ
  ฉบับที่แทนค่าแล้ว (ลูกค้าค้นด้วยสิ่งที่เขาเห็น) · **หน้าแก้ของแอดมินได้ฉบับดิบ** พร้อมรายการตัวแปรที่ใช้ได้
- **ตัวแปรที่พิมพ์ผิดถูกปฏิเสธตอนบันทึก (422 บอกช่องที่ผิด)** — ไม่ปล่อยให้ลูกค้าเห็น `{{shiping.rate}}`
- วิธีที่ร้านปิดไว้ **ไม่โผล่ในนโยบาย** (ปิด "ส่งวันเดียวกัน" แล้วบทความยังโฆษณา = ลูกค้าคิดว่าระบบพัง)
- migration `20261008091000_shipping_article_live_rates` แปลงบทความเดิม **เฉพาะเมื่อข้อความยังตรงกับต้นฉบับ
  ทุกตัวอักษร** — บทความที่แอดมินเขียนใหม่ไปแล้วไม่ถูกแตะ (แพตเทิร์นเดียวกับ STEP 43)
- AI Customer Service ใช้ `describeShippingRates()` ตัวเดียวกับบทความ — ถามสองทางได้คำตอบเดียวกัน

## พัสดุ

```
SHIPPED ──▶ IN_TRANSIT ──▶ FAILED ──▶ IN_TRANSIT (ขนส่งนำส่งใหม่)
   │             │            │
   └─────────────┴────────────┴──▶ RETURNED (ตีกลับถึงร้าน — จบ)

DELIVERED: ทางเดียวคือเปลี่ยนสถานะคำสั่งซื้อเป็น "ได้รับสินค้าแล้ว" (ได้เงิน COD + แต้ม + แจ้งชวนรีวิว)
```

| พัสดุล่าสุด                              | คำสั่งซื้อทำอะไรได้                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------- |
| ยังอยู่กับขนส่ง (ส่งออก/ขนส่ง/ไม่สำเร็จ) | กดส่งถึงได้ · **ยกเลิกไม่ได้** (ของยังไม่กลับมา จะ "รับเข้าคลัง" ไม่ได้)      |
| ตีกลับถึงร้านแล้ว                        | **ส่งใหม่** (พัสดุชิ้นใหม่) หรือ **ยกเลิก** (รับของเข้าคลัง) · กดส่งถึงไม่ได้ |

- ตารางนี้อยู่ที่ `shippingOrderActions()` ที่เดียว — ทั้ง `allowedNextStatuses` ของหลังบ้านและด่านที่ server ใช้
- **ส่งไม่สำเร็จ/ตีกลับต้องเขียนข้อความถึงลูกค้า** — แสดงในหน้าคำสั่งซื้อและในการแจ้งเตือน
- **ประวัติสถานะเป็นตาราง `ShipmentEvent` (append-only)** — ส่งไม่สำเร็จแล้วนำส่งใหม่ได้หลายรอบ
  คอลัมน์เวลาเดียวต่อสถานะเก็บความจริงไม่พอ · เรียงด้วย `sequence` ไม่ใช่ `createdAt` (บทเรียน STEP 42)
  · ประวัติของพัสดุที่สร้างก่อน STEP นี้ถูกเติมจากเวลาที่บันทึกไว้จริงเท่านั้น (ส่งออก · ส่งถึง)
- **ส่งใหม่** ไม่ตัดสต็อกซ้ำ (ของชิ้นเดิมที่กลับมาคือของที่ส่งออกไปใหม่) และไม่เก็บค่าส่งเพิ่ม (`fee = 0`)
  · เลขพัสดุใหม่เขียน cache `Order.trackingNumber` ในทรานแซกชันเดียวกัน · แจ้งลูกค้าเลขใหม่
- **แก้เลขที่กรอกผิด** ต้องมีเหตุผล · AdminLog เก็บเฉพาะช่องที่เปลี่ยนจริง · เปลี่ยนเลขหรือขนส่งแล้วแจ้งลูกค้า
- **ยกเลิกใบที่พัสดุตีกลับ**: รับของเข้าคลัง (`restockForOrder`) · คืนแต้ม · คืนโควตาคูปอง · COD ไม่ถูกนับว่าได้เงิน
  · ใบที่จ่ายผ่าน Stripe แล้วไปอยู่คิว "รอคืนเงิน" ของ STEP 43
- **ส่งถึงแล้ว** ปิดเฉพาะพัสดุที่ยังอยู่กับขนส่ง — ชิ้นที่ตีกลับไปแล้วคงสถานะ "ตีกลับ" ไว้ตามจริง
  (เดิมตั้งทุกแถวเป็น DELIVERED ซึ่งถูกเฉพาะตอนที่หนึ่งใบมีพัสดุชิ้นเดียว)
- **ล็อกแถวคำสั่งซื้อ (`FOR UPDATE`) ก่อนตัดสินทุกครั้ง** ทั้งการเปลี่ยนสถานะคำสั่งซื้อและสถานะพัสดุ
  — เดิมแค่ "อ่านสถานะซ้ำในทรานแซกชัน" ซึ่งไม่กันสองคนกดพร้อมกัน (ทั้งคู่อ่านได้ค่าเดิมก่อนอีกฝ่าย commit)
- **"เลยกำหนดส่ง" นับเฉพาะพัสดุที่ร้านกรอกกำหนดส่งไว้** — ไม่มีกำหนดส่ง = ไม่ถือว่าเลย (ระบบไม่เดาเวลาส่งถึง)
  · ฟอร์มส่งของมีช่องกำหนดส่งแล้ว (API รับมาตั้งแต่ STEP 13 แต่ฟอร์มไม่เคยมีช่องนี้)
- **ลิงก์ติดตามรับเฉพาะ `https://`** — `z.url()` เดิมยอม `javascript:` และ `http:` ซึ่งถูกแสดงเป็นลิงก์
  ในหน้าคำสั่งซื้อของลูกค้า
- ค้นจากเลขคำสั่งซื้อหาจากตาราง Order ก่อนแล้วใช้เป็น `IN` — ไม่เขียน OR ข้ามสองตาราง (กฎ STEP 34 ข้อ 2)

## ที่ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ยังไม่ต่อ API ของบริษัทขนส่ง** — สถานะพัสดุเป็นสิ่งที่พนักงานบันทึก ไม่ได้ดึงจากขนส่งอัตโนมัติ
  (ไม่มีบัญชีทดสอบให้ยืนยันกับของจริง — กฎเดียวกับ Stripe Refund ของ STEP 43) · ยังไม่มี STEP ไหนรับงานนี้ไว้
- **ยังไม่มีการพิมพ์ใบปะหน้าพัสดุ/ใบแพ็กของ** — ยังไม่มี STEP ไหนรับงานนี้ไว้
- **ยังไม่มีตารางผู้ให้บริการขนส่ง** — ชื่อขนส่งยังเป็นข้อความที่พนักงานพิมพ์ และลิงก์ติดตามกรอกเอง
  (ไม่ใส่รูปแบบลิงก์ของขนส่งแต่ละเจ้าไว้ในโค้ด เพราะยืนยันไม่ได้ว่ายังถูกต้อง — ลิงก์ผิดคือการพาลูกค้าไปผิดที่)
- **ค่าส่งยังเป็นอัตราเดียวต่อวิธี** — ไม่คิดตามน้ำหนัก/ขนาด/ระยะทาง และยังไม่มีอัตราแยกตามโซน
- **ช่องจังหวัดในที่อยู่ของลูกค้ายังเป็นข้อความอิสระ** — ลูกค้าที่พิมพ์ "กทม" เลือก "ส่งวันเดียวกัน" ไม่ได้
  (ฟอร์มบอกเหตุผลแล้ว) · การเปลี่ยนเป็นรายการเลือกต้องจัดการที่อยู่ที่บันทึกไว้แล้วด้วย · ยังไม่มี STEP ไหนรับงานนี้ไว้
- **รับที่ร้าน (PICKUP) ยังต้องกรอกขนส่ง + เลขพัสดุตอนเปลี่ยนเป็น "จัดส่งแล้ว"** เหมือนวิธีอื่น (กฎ STEP 13 ข้อ 2)
- **ไม่ปิดพัสดุที่เลยกำหนดเองตามเวลา** — ต้องมี job ตามเวลา (STEP 52) · ตอนนี้เป็นตัวกรองให้พนักงานตาม
