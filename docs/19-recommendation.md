# 19 — AI Recommendation Engine (STEP 46)

> แนะนำจากสิ่งที่ลูกค้าทำจริง · ทุกชิ้นบอกเหตุผล · ไม่มีประวัติ/ปิดไว้ = บอกว่าเป็นยอดนิยม · และสิ่งที่ยังไม่ได้ทำ

```
/                         → "แนะนำสำหรับคุณ" (มีประวัติ) หรือ "ยอดนิยมในร้าน" (ไม่มี/ไม่ล็อกอิน/ปิดไว้)
/product/[slug]           → ซื้อด้วยกันบ่อย · แมตช์ในลุค · สินค้าคล้ายกัน
/account/profile          → สวิตช์ "ให้ระบบแนะนำสินค้าจากพฤติกรรมของฉัน" (มีผลจริงแล้ว)

GET /api/recommendations/for-you?limit=      (ล็อกอินถ้ามี · Cache-Control: private, no-store)
GET /api/products/:slug/recommendations      (สาธารณะ — ไม่มีข้อมูลรายบุคคล)
```

## จุดเริ่มต้น

- ส่วน **"แนะนำสำหรับคุณ"** บนหน้าแรกคือ `/api/products?sort=popular` — รายการเดียวกันสำหรับทุกคน
  พร้อมข้อความ "การแนะนำเฉพาะบุคคลจะเปิดใน STEP 46"
- **สวิตช์ "ให้ระบบแนะนำสินค้าจากพฤติกรรมของฉัน" ในหน้าโปรไฟล์ไม่มีผลอะไรเลย** — บันทึกลงฐานข้อมูลได้
  แต่ไม่มีโค้ดไหนอ่านค่านี้ (ปัญหาชนิดเดียวกับคอลัมน์ที่ไม่มีใครเขียน — STEP 15/25/29/40)
- "สินค้าที่เกี่ยวข้อง" ในหน้าสินค้าคือยอดนิยมในหมวดเดียวกัน
- **เปิดหน้าสินค้าหนึ่งครั้ง = `UPDATE "Product" … viewCount + 1`** ผ่าน `prisma.product.update`
  → เขียนในเส้นทางอ่าน (บันทึกไว้ตอน STEP 34) **และ `updatedAt` ขยับทุกครั้งที่มีคนเปิดดู**
  หลังบ้านเรียงรายการสินค้าตาม `updatedAt` จึงเรียงตาม "ลูกค้าเปิดดูล่าสุด" แทน "แก้ไขล่าสุด"
  — บทความคลังความรู้ (`/faq` เรียงตาม `updatedAt`) เป็นแบบเดียวกันทั้งการเปิดอ่านและการโหวต
- **AI Stylist (fallback) ตอบว่า "คัดสรรชุดสำหรับสไตล์ X มาให้แล้ว"** แม้ของที่ได้เป็นยอดนิยมที่ไม่ตรงเงื่อนไขเลย
  (ค้นไม่เจอแล้วถอยไปยอดนิยมเงียบ ๆ) และกรองด้วย `totalStock` ก่อน `take` จึงได้ของน้อยกว่าที่ขอเมื่อของถูกจองหมด

## ทำไมไม่ใช้ LLM

1. **ทุกคำแนะนำต้องอธิบายได้ด้วยสินค้าจริงที่ลูกค้ารู้จัก** — "คล้าย “ฮู้ดดี้” ที่คุณถูกใจ"
   LLM แต่งเหตุผลที่ฟังดูดีแต่ไม่จริงได้ (กฎ "AI ห้ามแต่ง" ของทั้งโปรเจกต์)
2. หน้าแรกเปิดทุกครั้ง = เรียกทุกครั้ง · ค่าใช้จ่ายต่อการเปิดหน้าไม่คุ้มกับการเรียงสินค้าหลักสิบชิ้น
3. ทำงานเหมือนกันทุกครั้งไม่ว่ามี `OPENAI_API_KEY` หรือไม่ (Intelligent Fallback ของทั้งโปรเจกต์)

| ------------------------ | ------: | ------------------------------------------------------------------ |
| สั่งซื้อ                 |       3 | `OrderItem` ของใบที่ไม่ถูกยกเลิก/คืนเงิน                           |
| รีวิวว่าชอบ (4–5 ดาว)    |     2.5 | `Review` ที่ยังไม่ถูกลบ                                            |
| กดถูกใจ                  |       2 | `Wishlist`                                                         |

คะแนนของสินค้าที่อาจแนะนำ = หมวด + หมวดแม่ + แบรนด์ + tag ที่ตรงกับความชอบ + ความใกล้ของราคา
**+ ซื้อด้วยกัน** (ลูกค้าคนอื่นซื้อชิ้นนี้ในใบเดียวกับสิ่งที่ลูกค้าสนใจ — น้ำหนักมากสุด เพราะเป็นพฤติกรรมจริง ไม่ใช่การเดาจากหมวด)

| เหตุผลใต้การ์ด                                                    | เมื่อไร                                                             |
| ----------------------------------------------------------------- | ------------------------------------------------------------------- |
| `ลูกค้าที่ซื้อ “X” ซื้อชิ้นนี้ด้วย`                               | คะแนนจากการซื้อด้วยกันมากกว่าคะแนนจากความคล้าย                      |
| `คล้าย “X” ที่คุณถูกใจ` (สั่งซื้อ · รีวิวว่าชอบ · ในตะกร้าของคุณ) | X = สัญญาณที่ใกล้กับชิ้นนี้ที่สุด (หมวด · หมวดแม่ · แบรนด์ · tag)   |
| `ยอดนิยมในร้าน`                                                   | ชิ้นที่เติมให้ครบจำนวน — **บอกว่าเป็นยอดนิยม ไม่แต่งเหตุผลส่วนตัว** |

## โหมดของ "แนะนำสำหรับคุณ"

| สถานการณ์                            | `mode`     | `fallbackReason` | หัวข้อบนหน้าแรก                   |
| ------------------------------------ | ---------- | ---------------- | --------------------------------- |
| มีประวัติและมีของที่ใกล้เคียง        | `PERSONAL` | `null`           | แนะนำสำหรับคุณ                    |
| ไม่ได้ล็อกอิน                        | `POPULAR`  | `GUEST`          | ยอดนิยมในร้าน                     |
| ปิดสวิตช์ในหน้าโปรไฟล์               | `POPULAR`  | `OPTED_OUT`      | ยอดนิยมในร้าน + ลิงก์ไปเปิดสวิตช์ |
| ยังไม่มีประวัติ                      | `POPULAR`  | `NO_HISTORY`     | ยอดนิยมในร้าน                     |
| มีประวัติแต่ไม่มีของที่ใกล้และขายได้ | `POPULAR`  | `NO_MATCH`       | ยอดนิยมในร้าน                     |

ยอดนิยม = จำนวนคนกดถูกใจ → ยอดขาย (ใบที่ได้เงินแล้ว) → ยอดเข้าชม → วันที่เปิดขาย · เฉพาะของที่ขายได้จริง

## กฎที่ห้ามละเมิด

1. **สวิตช์ปิดการแนะนำต้องมีผลจริง — ปิดแล้ว "ไม่อ่านประวัติเลย" ไม่ใช่ "อ่านแล้วไม่โชว์"**
   `recommendForUser` ตรวจ `allowPersonalization` **ก่อน** `loadSignals()` · มีเทสต์ที่ให้คนที่ปิดไว้มีประวัติ
   เหมือนลูกค้าอีกคน แล้วยืนยันว่าได้รายการ **เดียวกับคนที่ไม่ได้ล็อกอินเป๊ะ**
2. **โหมดยอดนิยมห้ามเรียกตัวเองว่า "สำหรับคุณ"** — ติดป้าย "สำหรับคุณ" ให้รายการที่ทุกคนเห็นเหมือนกัน
   คือการบอกว่าระบบรู้จักเขา และคนที่ปิดสวิตช์จะเข้าใจว่าสวิตช์ไม่มีผล
   (`forYouHeading()` ใน [features/home/lib/for-you.ts](../frontend/src/features/home/lib/for-you.ts) · มีเทสต์ทุกเหตุผล)
   · **ตอนโหลดและตอนโหลดไม่สำเร็จใช้หัวข้อกลาง "สินค้าแนะนำ"** — เดิม skeleton เขียน "แนะนำสำหรับคุณ" ให้ทุกคน
   คนที่ไม่ได้ล็อกอินจึงเห็นแวบหนึ่งก่อนเปลี่ยนเป็นยอดนิยม (เจอตอนตรวจ HTML ที่เรนเดอร์จริง)
3. **เหตุผลทุกบรรทัดมาจาก backend และอ้างสินค้าจริง** — หน้าเว็บไม่แต่งเหตุผลเอง
   ตรงแค่แบรนด์ก็ต้องอ้างสินค้าที่แบรนด์เดียวกัน (เคยตกไปเป็น "หมวดที่คุณสนใจ" ซึ่งไม่จริง — แก้ระหว่างเขียน)
4. **"ซื้อด้วยกัน" นับเฉพาะใบที่ร้านได้เงินแล้ว** (`paymentStatus = PAID` และไม่ถูกยกเลิก/คืนเงิน)
   ใบค้างจ่ายสร้างรัว ๆ ได้ฟรี — ถ้านับ ใครก็ปั่นให้สินค้าของตัวเองขึ้นเป็น "ซื้อด้วยกันบ่อย" ได้ (มีเทสต์ใบค้างจ่าย)
   · **ไม่นับใบของลูกค้าคนนั้นเอง** ในหน้า "สำหรับคุณ" (ของที่เขาซื้อเองไม่ใช่สิ่งที่ "คนอื่นซื้อด้วยกัน")
5. **แนะนำเฉพาะของที่ขายได้จริง** — `HAS_AVAILABLE_STOCK_SQL` ตอนเลือกผู้สมัคร + ตัด `OUT_OF_STOCK` อีกชั้นตอนสร้างการ์ด
   (`toProductCards` — กฎ STEP 15) · พาลูกค้าไปเจอของที่ซื้อไม่ได้คือทางตัน
6. **ไม่แนะนำสิ่งที่ลูกค้ารู้จักแล้ว** (ซื้อ · ถูกใจ · ในตะกร้า · รีวิวแล้ว) · หน้าสินค้าไม่แนะนำตัวเอง
   · **รีวิว 1–2 ดาว = ไม่ชอบ** → ชิ้นนั้นถูกตัดออกจากสัญญาณทุกทาง (รวมการสั่งซื้อ) และจากรายการยอดนิยมที่เติมให้
   เดิมนับเฉพาะรีวิว 4–5 ดาวเป็นสัญญาณแต่ไม่ได้ตัดการสั่งซื้อ จึงได้ "คล้าย “X” ที่คุณสั่งซื้อ" กับของที่ลูกค้าบอกว่าแย่
   (เจอระหว่างเขียนเอกสารนี้ — มีเทสต์ทั้งระดับกฎและผ่าน HTTP) · มีประวัติแต่ทั้งหมดเป็นของที่ไม่ชอบ → `NO_MATCH` ไม่ใช่ `NO_HISTORY`
7. **ลำดับต้องคงที่** — คะแนนเท่ากันเรียงด้วย id (เปิดหน้าซ้ำแล้วรายการไม่สลับไปมา)
8. **"สำหรับคุณ" ของคนที่ล็อกอินห้ามแคชร่วมกัน** — backend ตอบ `Cache-Control: private, no-store`
   และหน้าเว็บยิงด้วย `apiFetchAsUser` + `no-store` · ไม่ล็อกอิน (ยอดนิยมชุดเดียวกันทุกคน) แคช 60 วินาทีได้
9. **ไม่มีช่องให้ client ส่งสัญญาณหรือ userId มาเอง** — validator รับแค่ `limit` · ตัวตนมาจาก session เท่านั้น

## ยอดเข้าชม — [view-counter.service.ts](../backend/src/services/view-counter.service.ts)

- เปิดหน้าสินค้า → นับในหน่วยความจำ → เขียนครั้งเดียวทุก 5 วินาทีด้วย SQL ตรง
  (`UPDATE … FROM unnest(ids, counts)`) ซึ่ง **ไม่แตะ `updatedAt`**
- ปิด server แบบปกติ → `server.ts` เขียนยอดที่ค้างก่อนตัดฐานข้อมูล
- ⚠️ process ตายกะทันหัน → ยอดไม่เกิน 5 วินาทีสุดท้ายหาย — **ยอมรับได้** เพราะยอดเข้าชมเป็นสัญญาณความนิยมโดยประมาณ
  ไม่ใช่เงินหรือสต็อก · หลาย instance ก็ถูกต้องเพราะทุกชุดเป็นการ "บวกเพิ่ม"
- เขียนไม่สำเร็จ → log ระดับ warn แล้วทิ้งชุดนั้น · **การนับยอดล้มต้องไม่ทำให้การเปิดหน้าสินค้าล้ม**
- บทความคลังความรู้: เปิดอ่าน/โหวต ยังเขียนทันที (มีคนกดน้อยกว่ามาก) แต่ **ส่ง `updatedAt` เดิมกลับไป**

## AI Stylist — บอกตรง ๆ เมื่อของไม่ตรงเงื่อนไข

`searchProductsForStylist()` คืน `{ products, relaxed }` · `relaxed = true` = ไม่พบของที่ตรงทุกเงื่อนไข
จึงคืนยอดนิยมที่ขายได้แทน → ข้อความตอบเขียนว่า **"สินค้ายอดนิยมของร้านที่ไม่ได้ตรงเงื่อนไขทั้งหมด"**
และเครื่องมือที่ส่งให้ OpenAI แนบ `matchedAllConditions: false` (ไม่งั้น LLM จะเล่าว่าเป็นของที่ลูกค้าขอ)
· ตัวกรอง `totalStock` ในคิวรีเป็นแค่การคัดชุดใหญ่ (ดึง 3 เท่าของที่ต้องการ) แล้วตัดด้วยจำนวนที่ขายได้จริง

## ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ไม่มีสัญญาณ "เคยเปิดดู"** — ยอดเข้าชมนับรวมต่อสินค้า ไม่ได้เก็บว่า **ใคร** เปิดอะไร
  การเก็บประวัติการเปิดดูรายคนคือข้อมูลส่วนบุคคลชุดใหม่ (ต้องมีนโยบายอายุการเก็บ — STEP 53) จึงยังไม่ทำ
- **"ซื้อด้วยกัน" คำนวณสดทุกคำขอ** (OrderItem self-join) — วัดที่ข้อมูลปริมาณจริงแล้วอยู่ในงบ
  (ดู [10-performance.md](10-performance.md)) ถ้าคำสั่งซื้อโตเป็นหลักล้านต้องย้ายไปตารางสรุปที่คิดเป็นรอบ
- **ผู้สมัครจำกัด 400 ชิ้นต่อคำขอ** — แคตตาล็อกหลักหมื่นที่ความชอบกว้างมากอาจตกหล่นชิ้นที่ดีกว่า
- ยังไม่มีส่วนแนะนำในตะกร้า/หลังชำระเงิน · `Look.viewCount` ยังเขียนทันทีที่เปิดหน้าลุค ·
