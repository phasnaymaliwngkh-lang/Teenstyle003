# 20 — Image Management (STEP 47)

> อัปโหลดรูปสินค้าและรูปรีวิวได้จริง · ทุกไฟล์ถูกแปลงใหม่และตัดข้อมูลตำแหน่งออก · ไฟล์ที่เลิกใช้ลบได้อย่างปลอดภัย · และสิ่งที่ยังไม่ได้ทำ

```
/admin/products/[id]   → ส่วน "รูปสินค้า": อัปโหลด · คำอธิบายรูป · เรียงลำดับ (รูปแรก = รูปหลัก) · ถอดรูป
/admin/media           → คลังรูป: ไฟล์ทั้งหมด ใช้อยู่ที่ไหน · ลบไฟล์ที่ไม่ได้ใช้แล้ว (media:manage)
/product/[slug]        → ฟอร์มรีวิวแนบรูปได้ 4 รูป · รูปขึ้นหน้าสินค้าหลังร้านตรวจพร้อมรีวิว
/admin/reviews         → เห็นรูปตอนตรวจรีวิว

GET    /api/admin/products/:id/images            PUT /api/admin/products/:id/images/order
POST   /api/admin/products/:id/images (file+alt) PATCH|DELETE /api/admin/products/:id/images/:imageId
POST   /api/reviews/:id/images (file)            DELETE /api/reviews/:id/images/:imageId
GET    /api/admin/media                          POST /api/admin/media/purge
GET    /media/<storageKey>                       ← ไฟล์จริง (backend เสิร์ฟ · frontend rewrite path เดียวกัน)
```

## จุดเริ่มต้น

- **รูปสินค้าคือช่องให้วางลิงก์** จาก Unsplash/Google เท่านั้น — ร้านไม่มีทางใส่รูปที่ถ่ายเอง
- **บันทึกฟอร์มสินค้า = ลบรูปทั้งชุดแล้วสร้างใหม่** จากรายการในฟอร์ม
- `ProductImage.publicId` จองไว้ให้ Cloudinary แต่ไม่มีโค้ดไหนเขียน (ว่างทุกแถว) ·
  ตัวแปร `CLOUDINARY_*` อยู่ใน `.env.example` และ compose แต่ไม่มีโค้ดไหนอ่าน
- `Review.images` ว่างเสมอ — ลูกค้าแนบรูปไม่ได้ (หนี้ที่ STEP 23 กันไว้: "ห้ามแก้ด้วยการรับ URL จาก client")
- **ปุ่มนำเข้า/ส่งออกของหลังบ้านยิง `publicEnv.apiUrl` ตรง ๆ** ไม่ผ่าน proxy path →
  ตอน production เป็นคำขอข้ามโดเมน เบราว์เซอร์บล็อก cookie แล้วได้ 401 ทุกครั้ง (เจอตอนเพิ่มการอัปโหลดรูป)
- **รัน `npm run db:seed` ซ้ำ = ลบรูปของสินค้าตัวอย่างทั้งหมดแล้วสร้างลิงก์ Unsplash ใหม่** —
  ถ้าร้านอัปโหลดรูปจริงให้สินค้าตัวอย่างแล้ว รูปจะหายเงียบ ๆ (ทั้งที่เอกสาร deploy บอกให้รัน seed ซ้ำ)

## ทำไมไม่ใช้ Cloudinary

เครื่องนี้ไม่มีบัญชี Cloudinary ให้ยืนยันกับของจริง — **การเขียน adapter ที่ทดสอบกับของจริงไม่ได้เลย
แย่กว่าการบอกความจริง** (กฎเดียวกับ Redis ของ STEP 34 และ Stripe Refund ของ STEP 43)
ไฟล์จึงอยู่บนดิสก์ของ backend (`UPLOAD_DIR`) ซึ่งทดสอบได้ทั้งหมด · ตัวแปร `CLOUDINARY_*` ถูกถอดออก
เพราะการมี env ที่ตั้งแล้วไม่เกิดอะไรขึ้นคือการหลอกคนตั้งว่ารูปไปอยู่บน Cloudinary แล้ว

ที่เก็บไฟล์อยู่ใน [media-storage.ts](../backend/src/services/media-storage.ts) **ที่เดียว**
(`writeMediaFile` · `removeMediaFile`) — ส่วนอื่นของระบบรู้จักแค่ `storageKey` กับ url
ย้ายไป object storage = เปลี่ยนไฟล์นี้ + การเสิร์ฟ `/media` ใน `app.ts`

## เส้นทางของไฟล์หนึ่งไฟล์

```
เบราว์เซอร์ ──multipart──▶ multer (หน่วยความจำ · 1 ไฟล์ · ≤ 8MB · mimetype ที่เห็นชัดว่าไม่ใช่รูป = 400)
   ▶ processImage()  อ่านหัวไฟล์ → checkSourceImage() → ถอดรหัส → หมุนตาม EXIF → ย่อ → WebP (ไม่มี metadata)
   ▶ writeMediaFile() เขียนไฟล์ชั่วคราว แล้ว rename (ไม่มีใครเห็นไฟล์ครึ่ง ๆ)
   ▶ $transaction: แถว MediaAsset + ผูกกับสินค้า/รีวิว (ล็อกแถวก่อนนับเพดาน)
   ▶ ล้มตรงไหน → ลบไฟล์ที่เพิ่งเขียน
```

| การใช้งาน | ด้านสั้นขั้นต่ำ | ด้านยาวสูงสุดหลังย่อ | คุณภาพ WebP | เพดานต่อชิ้น |
| --------- | --------------: | -------------------: | ----------: | -----------: |
| รูปสินค้า |          600 px |              2000 px |          82 |       10 รูป |
| รูปรีวิว  |          200 px |              1600 px |          80 |        4 รูป |

รับ JPEG · PNG · WebP · AVIF (ตัดสินจาก **เนื้อไฟล์** ที่ sharp อ่าน) · ไม่รับ GIF · SVG · HEIC ·
รูปเคลื่อนไหว · รูปเกิน 40 ล้านพิกเซล (decompression bomb — PNG สีเดียว 30,000×30,000 มีขนาดไฟล์ไม่กี่ร้อย KB)

## การแสดงรูป — ทำไม url เป็น `/media/...` ไม่ใช่โดเมนของ backend

Next 16 **ไม่ย่อรูปจาก IP ภายใน** (`dangerouslyAllowLocalIP` = false) — backend ตอน dev คือ localhost
และใน docker network คือ IP ภายใน การเปิดค่านั้นคือเปิดช่อง SSRF ให้ตัวย่อรูปยิงเข้าเครือข่ายภายใน
→ url ในฐานข้อมูลเป็น path ของเว็บเราเอง (`/media/...`) แล้ว `next.config.ts` rewrite ไป backend
· `images.localPatterns` อนุญาต `/media/**` **ห้ามมี query** (ทดสอบแล้ว: ใส่ `?x=1` ได้ 400)
· JSON-LD ใช้ `absoluteUrl()` อยู่แล้ว จึงได้ url เต็มของโดเมนร้าน

## กฎที่ห้ามละเมิด

1. **ไม่เก็บไฟล์ที่ผู้ใช้ส่งมาตรง ๆ** — แปลงใหม่ทุกไฟล์ ผลคือ EXIF ทั้งก้อนหายไป
   (รวม **พิกัด GPS ของบ้านลูกค้า** ที่ติดมากับรูปจากมือถือ) และไฟล์ที่ซ่อนของอื่นในเนื้อรูปรอดออกมาไม่ได้
2. **ตัดสินชนิดจากเนื้อไฟล์** — mimetype/นามสกุลผู้ใช้ตั้งเองได้ (มีเทสต์: HTML ที่ส่งมาเป็น `image/jpeg` = 400)
3. **รูปแบบของ `storageKey` มีที่เดียว** ([media.model.ts](../backend/src/models/media.model.ts)) —
   ตัวสร้าง ตัวอ่าน id กลับ และตัวตรวจตอนเสิร์ฟ ใช้ชุดเดียวกัน (บทเรียน STEP 40) · ไม่มีส่วนไหนมาจากชื่อไฟล์ของผู้ใช้
4. **`/media` อยู่ก่อน rate limit** — รูปทั้งร้านมาจาก IP ของ server frontend ตัวเดียว (rewrite + ตัวย่อรูป)
   ถ้านับรวมกับ limit ต่อ IP รูปจะหายทั้งร้านเมื่อมีคนเข้ามาก (กฎ STEP 29) · มีเทสต์ตรวจลำดับใน stack
5. **เสิร์ฟเฉพาะ path ที่ระบบสร้าง** — ไฟล์ชั่วคราวระหว่างเขียน (`.tmp`) อยู่โฟลเดอร์เดียวกันแต่เปิดไม่ได้
6. **รูปแรก = รูปหลัก** — การ์ด ตะกร้า คำสั่งซื้อ ลุค ป้ายบาร์โค้ดเลือกด้วย `isMain` ส่วนหน้าสินค้าเรียงด้วย `sortOrder`
   ถ้าไม่ตรงกันการ์ดกับหน้าสินค้าโชว์คนละรูป · "ตั้งเป็นรูปหลัก" = ย้ายขึ้นลำดับแรก ·
   unique index `ProductImage_one_main_per_product` เป็นด่านสุดท้าย (partial index — ประกาศใน schema ไม่ได้)
7. **เรียงใหม่ต้องส่งรูปครบทุกรูป ไม่งั้น 409** — หน้าจอของคนกดอาจเห็นรูปไม่ครบ (มีคนเพิ่ม/ถอดพร้อมกัน)
8. **PATCH สินค้าไม่รับ `images` แล้ว** — "แทนที่ทั้งชุด" จะลบรูปที่อัปโหลดไว้ถ้าคนส่งไม่ได้ใส่กลับมา
9. **แนบหรือถอดรูปรีวิว = กลับไปรอตรวจ** (กฎเดียวกับแก้ข้อความ STEP 23 ข้อ 3) ·
   หลังบ้านเห็นรูปตอนตรวจ · หน้าร้านเห็นรูปเฉพาะรีวิวที่อนุมัติ · **เขียนรีวิวใหม่หลังลบ = รูปเก่าไม่กลับมา**
10. **ถอดรูปไม่ลบไฟล์** — ดูหัวข้อถัดไป
11. **seed ไม่แตะรูปของสินค้าที่ร้านอัปโหลดเองแล้ว** (url ขึ้นต้นด้วย `/media/`)

## ลบไฟล์อย่างไรไม่ให้ประวัติคำสั่งซื้อเป็นรูปแตก

url ของรูปหลักถูกคัดลอกเป็น snapshot ใน `OrderItem.imageUrl` ตอนสั่งซื้อ (STEP 10 ข้อ 5)
→ **ไฟล์ที่ถอดออกจากสินค้าแล้วอาจยังอยู่ในประวัติคำสั่งซื้อของลูกค้า** ลบทันทีคือรูปแตก

ทำแบบ mark & sweep ([media.service.ts](../backend/src/services/media.service.ts))

| ขั้น  | ทำอะไร                                                                                                  |
| ----- | ------------------------------------------------------------------------------------------------------- |
| mark  | ตอนถอดรูป/ลบรีวิว และตอนกดล้าง: ไฟล์ที่ไม่มีที่ไหนใช้ได้ `unusedSince` · ไฟล์ที่กลับมาถูกใช้ล้างค่ากลับ |
| sweep | กดล้างที่ `/admin/media`: ลบไฟล์ที่ไม่ถูกใช้ต่อเนื่องเกิน **24 ชั่วโมง** (ตรวจซ้ำในทรานแซกชันที่ลบ)     |

"ใช้อยู่" = url ปรากฏใน `ProductImage` (รวมสินค้าที่ถูกลบแบบซ่อน) · `OrderItem.imageUrl` ·
รีวิวที่ยังไม่ถูกลบ · `Category.imageUrl` · `Look.imageUrl` · `User.image` (สามอย่างหลังยังอัปโหลดไม่ได้ แต่นับไว้ก่อน)
**เพิ่มที่เก็บ url รูปแห่งใหม่ ต้องเพิ่มขาใน `usedMediaUrlsSql()`** ไม่งั้นตัวล้างจะลบไฟล์ที่ยังใช้อยู่

ช่วงผ่อนผันมีไว้กันกรณีจริง: คำสั่งซื้อที่กำลังสร้างอ่าน url ไปแล้ว แล้วเขียน `OrderItem` หลังรูปถูกถอดไม่กี่มิลลิวินาที
· หน้าคลังรูป **อ่านอย่างเดียว** (มีเทสต์ยืนยันว่าเปิดดูแล้ว `unusedSince` ไม่ขยับ — บทเรียน STEP 46)
· ลบแถวก่อน แล้วลบไฟล์หลัง commit — ลบไฟล์ล้ม = ไฟล์กำพร้าบนดิสก์ (กินที่) ไม่ใช่รูปแตกให้ลูกค้าเห็น

## Deploy

- `UPLOAD_DIR` ต้องเป็น **volume ถาวร** (compose ผูก `uploads:/app/uploads` แล้ว · Dockerfile สร้างโฟลเดอร์ให้ user `node`)
- **รัน backend ได้ instance เดียว** จนกว่าจะย้ายที่เก็บไป object storage
- **backup ต้องรวมโฟลเดอร์นี้** (STEP 50) — restore แค่ฐานข้อมูลได้แถว `MediaAsset` ที่ไม่มีไฟล์
- frontend rewrite `/media/:path*` ไป `NEXT_PUBLIC_API_URL` เสมอ (ไม่ขึ้นกับ `NEXT_PUBLIC_API_PROXY_PATH`)

## ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ยังไม่มี object storage / CDN** — ไฟล์อยู่บนดิสก์ของ backend · scale แนวนอนไม่ได้ (ดูหัวข้อ Deploy)
- **ยังไม่มีการล้างไฟล์ตามเวลา** — ต้องกดที่ `/admin/media` เอง · ให้ job ของ STEP 52 เรียก `purgeUnusedMedia()`
- **รูปโปรไฟล์ · รูปประกอบคำขอคืนสินค้า · รูปหมวดหมู่/ลุค ยังอัปโหลดไม่ได้** — ยังไม่มี STEP ไหนรับงานนี้ไว้
  (ถ้าทำ ต้องผ่าน `storeImage()` และเพิ่มขาใน `usedMediaUrlsSql()` ถ้าเป็นที่เก็บ url ใหม่)
- **ไม่มีการตรวจเนื้อหารูปอัตโนมัติ** — รูปรีวิวพึ่งการตรวจของคน (รีวิวทุกฉบับรอตรวจอยู่แล้ว)
- **รูปสินค้าตัวอย่างจาก seed ยังเป็นลิงก์ Unsplash** — ร้านเปลี่ยนเป็นรูปจริงได้ที่หน้าแก้ไขสินค้า
- **ไฟล์ที่ไม่มีแถว `MediaAsset`** (backend ล่มระหว่างเขียนไฟล์กับบันทึกแถว) ตัวล้างมองไม่เห็น — เกิดได้ยาก
  แต่ถ้าดิสก์โตผิดปกติ ต้องเทียบไฟล์ในโฟลเดอร์กับตารางเอง
