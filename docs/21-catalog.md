# 21 — Category / Brand / Size / Color (STEP 48)

> ร้านจัดการหมวดหมู่ แบรนด์ ไซซ์ และสีเองได้ · ทำอะไรไม่ได้ต้องบอกเหตุผลก่อนกด ·
> และสินค้าที่เปิดขายใช้ได้เฉพาะของที่เปิดใช้อยู่ ไม่ว่าจะแก้จากทางไหน

```
/admin/catalog                → แท็บ หมวดหมู่ · แบรนด์ · ไซซ์ · สี (ดู = product:read · แก้ = catalog:manage)
                                เพิ่ม · แก้ · ปิด/เปิดใช้งาน · ลบ · เลื่อนลำดับ · เห็นว่าแต่ละรายการถูกใช้อยู่เท่าไร

GET    /api/admin/catalog                           ← ภาพรวมทั้ง 4 ชนิด + การใช้งาน + เหตุผลที่ทำไม่ได้
POST   /api/admin/catalog/categories                PUT /api/admin/catalog/categories/order { parentId, ids }
PATCH|DELETE /api/admin/catalog/categories/:id
POST   /api/admin/catalog/brands                    PATCH|DELETE /api/admin/catalog/brands/:id
POST   /api/admin/catalog/sizes                     PUT /api/admin/catalog/sizes/order { ids }
PATCH|DELETE /api/admin/catalog/sizes/:id
POST   /api/admin/catalog/colors                    PUT /api/admin/catalog/colors/order { ids }
PATCH|DELETE /api/admin/catalog/colors/:id
```

ทุกคำขอที่เปลี่ยนข้อมูลตอบ **ภาพรวมชุดใหม่ทั้งชุด** หน้าเว็บจึงไม่ต้องเดาว่าตัวเลขการใช้งานหรือเหตุผลเปลี่ยนไปอย่างไร

## จุดเริ่มต้น

- **ไม่มีทางแก้หมวดหมู่ แบรนด์ ไซซ์ หรือสีเลย นอกจากแก้ seed แล้วรันใหม่** — ร้านเพิ่มสีใหม่ไม่ได้
- **seed เขียนทับทุกครั้งที่รัน** (`update: { name, sortOrder, parentId, isActive: true }`) —
  ถ้ามีหน้าจัดการโดยไม่แก้ข้อนี้ ทุกอย่างที่ร้านแก้จะย้อนกลับ และของที่ร้านปิดไว้จะกลับมาเปิดเองตอน deploy
- **FK ของ `ProductVariant.colorId/sizeId` เป็น `SetNull`** — ลบสีทิ้งแล้วตัวเลือกที่ใช้สีนั้นกลายเป็น "ไม่มีสี"
  เงียบ ๆ (และชน unique ของตัวเลือกอื่นในสินค้าเดียวกันที่ไม่มีสี)
- **นำเข้าไฟล์ด้วยสี/ไซซ์ที่สะกดผิด ข้ามไปเงียบ ๆ** — "แดด" แทน "แดง" ได้ตัวเลือกที่ไม่มีสี ไม่มี error
- **นำเข้าไฟล์ไม่ระบุสถานะ = `ACTIVE`** — สินค้าใหม่จากไฟล์ (ไม่มีรูป) เปิดขายทันทีแบบไม่มีภาพ
  และนำเข้าไฟล์ราคาใหม่แล้ว **สินค้าที่ร้านเก็บเข้าคลังไว้กลับมาขายเอง** · และไม่ตั้ง `publishedAt` ให้
- **แผงกรองของ `/shop` แสดงทุกสีที่เปิดใช้** ไม่ว่าจะมีสินค้าใช้หรือไม่ — พอร้านเพิ่มสีได้เอง
  สีใหม่จะโผล่ในตัวกรองทันทีทั้งที่กดแล้วได้หน้าว่าง
- `GET /api` ประกาศ `/api/brands` ว่า "จะมาใน STEP 48"

## ข้อตกลงหลักข้อเดียว

**สินค้าที่เปิดขายทุกชิ้นใช้หมวด แบรนด์ สี และไซซ์ที่เปิดใช้อยู่เท่านั้น**

ถ้าหลุด หน้าร้านจะขายของที่ลูกค้าหาไม่เจอ: ตัวกรองซ่อนหมวดที่ปิด แต่สินค้าในหมวดนั้นยังขายอยู่ ·
การ์ดสินค้าโชว์สีที่กดกรองไม่ได้ · ลิงก์ที่ลูกค้าแชร์ไว้ไปจบที่หน้าว่าง

รักษาไว้สองทาง และ **ทั้งสองทางล็อกแถวเดียวกัน**

| ทาง                       | ทำที่ไหน                                                                                              | ล็อก         |
| ------------------------- | ----------------------------------------------------------------------------------------------------- | ------------ |
| ปิด/ลบของที่ถูกใช้อยู่    | [catalog-admin.service.ts](../backend/src/services/catalog-admin.service.ts) → 409 + เหตุผล           | `FOR UPDATE` |
| ผูกของที่ปิดอยู่กับสินค้า | [catalog-guard.ts](../backend/src/services/catalog-guard.ts) `assertCatalogRefsActive()` → 400 + ชื่อ | `FOR SHARE`  |

`assertCatalogRefsActive()` ถูกเรียกทุกจุดที่ผูกของกับสินค้า: สร้าง/แก้สินค้า (หมวด · แบรนด์) ·
เพิ่มตัวเลือก (สี · ไซซ์) · **เปิดขายฉบับร่าง** (ตรวจทุกอย่างที่สินค้าใช้ รวมสี/ไซซ์ของตัวเลือกที่เปิดอยู่) ·
**เปิดตัวเลือกกลับมาขาย** · และนำเข้าจากไฟล์ (ตรวจซ้ำในทรานแซกชันที่บันทึกจริง)

### ⚠️ ทำไมการอ่าน `isActive` ธรรมดาไม่พอ

คนหนึ่งปิดหมวด ขณะที่อีกคนเปิดขายสินค้าในหมวดนั้น — ภายใต้ READ COMMITTED ทั้งคู่อ่านค่าเดิม
(หมวดยังเปิด · ยังไม่มีสินค้าขายในหมวด) แล้วผ่านการตรวจทั้งคู่ ผลคือสินค้าที่ขายอยู่ในหมวดที่ปิด
ล็อกแล้วฝั่งที่มาทีหลังต้องรอ และเห็นผลของฝั่งแรกก่อนตัดสิน · ลำดับการล็อกคงที่
(Category → Brand → Color → Size) กัน deadlock · มีเทสต์ยิงพร้อมกัน 3 รอบ และ
**เอา `FOR SHARE` หรือ `FOR UPDATE` ออกแล้วเทสต์ล้มจริง**

## กฎที่ห้ามละเมิด

1. **เหตุผลที่ "ทำไม่ได้" คิดที่ [models/catalog.model.ts](../backend/src/models/catalog.model.ts) ที่เดียว**
   (`categoryBlockers` · `brandBlockers` · `variantOptionBlockers`) — หน้าหลังบ้านได้รับมาใน `blockers`
   ปุ่มจึงปิดพร้อมเหตุผลตั้งแต่ก่อนกด · service ตัดสินจริงด้วยฟังก์ชันเดียวกันในทรานแซกชันที่ล็อกแถวแล้ว
   ข้อความจึงตรงกันเสมอ · **หน้าเว็บไม่คิดเหตุผลเอง**
2. **หมวดซ้อนได้ 2 ชั้นเท่านั้น** (หมวดแม่ → หมวดย่อย) — หน้าร้านกรองด้วย "หมวดนี้ + หมวดย่อยชั้นเดียว"
   (`searchProducts` · ตัวนับในแผงกรอง · การ์ดหมวดบนหน้าแรก) ชั้นที่ 3 จะหายจากหมวดบนสุดเงียบ ๆ
   · `checkCategoryParent()` ปฏิเสธ: หมวดหลาน · ย้ายหมวดที่มีลูกไปเป็นลูก · เป็นแม่ตัวเอง ·
   เปิดหมวดย่อยใต้หมวดแม่ที่ปิดอยู่ · ปิดหมวดแม่ที่ยังมีหมวดย่อยเปิดอยู่
3. **slug/รหัสแก้ได้เฉพาะตอนยังไม่มีสินค้า/ตัวเลือกใช้** (นับฉบับร่างด้วย) — อยู่ในลิงก์ที่ลูกค้าแชร์
   และ Google เก็บไว้ (`/shop?category=` · `?brand=` · `?color=` · `?size=`) และเป็นคำที่ตัวค้นหาตีความ
   · ฟอร์มแก้ **ส่งเฉพาะช่องที่เปลี่ยน** — ส่ง slug เดิมกลับไปด้วยจะถูกปฏิเสธทั้งที่ผู้ใช้แค่แก้ชื่อ
4. **ลบหมวด/แบรนด์ = soft delete + คืน slug (และชื่อแบรนด์) ให้ใช้ใหม่ได้** (`deletedSlug` · `deletedName`)
   — unique ของฐานข้อมูลนับแถวที่ลบแล้วด้วย ถ้าไม่เปลี่ยน ลบแบรนด์ "Nike" แล้วสร้าง "Nike" ใหม่ไม่ได้ตลอดไป
   · **ลบสี/ไซซ์ = ลบจริง ได้เฉพาะตอนไม่มีตัวเลือกไหนอ้างถึงเลย รวมตัวเลือกที่ถูกลบไปแล้ว**
   (ประวัติสินค้ายังอ้างถึง) · FK เป็น `Restrict` เป็นด่านสุดท้าย — ทางที่ถูกคือ "ปิดใช้งาน"
5. **ลบหมวดที่คูปองจำกัดไว้ไม่ได้** — คูปองที่ผูกกับหมวดที่หายไปจะใช้ไม่ได้เงียบ ๆ (ลูกค้าได้คำตอบว่า
   "ไม่มีสินค้าในตะกร้าที่ใช้คูปองนี้ได้" ทั้งที่ร้านตั้งใจแจก)
6. **ชื่อห้ามซ้ำแบบไม่สนตัวพิมพ์** — หมวด: ห้ามซ้ำในหมวดแม่เดียวกัน (ต่างหมวดแม่ใช้ชื่อเดียวกันได้) ·
   แบรนด์/สี/ไซซ์: ห้ามซ้ำทั้งร้าน · ค่าสีเก็บเป็น `#RRGGBB` ตัวพิมพ์ใหญ่ · รหัสไซซ์เป็นตัวพิมพ์ใหญ่
7. **เรียงลำดับต้องส่งรายการครบทุกตัวในกลุ่ม** (หมวด: กลุ่มเดียวกัน = หมวดแม่เดียวกัน) — ไม่ครบหรือมีของ
   กลุ่มอื่นปน = 409 · ส่งแค่ตัวที่ขยับทำให้ลำดับของตัวที่เหลือขึ้นกับว่าใครบันทึกก่อน · แบรนด์เรียงตามชื่อ
8. **ทุกการเปลี่ยนเขียน `AdminLog` ในทรานแซกชันเดียวกัน** (`catalog.<ชนิด>.create|update|delete|reorder`)
   · `before` กับ `after` มีคีย์ชุดเดียวกันเสมอ (กฎ STEP 27)
9. **seed สร้างเฉพาะที่ยังไม่มี** (`update: {}`) — รัน `npm run db:seed` ซ้ำแล้วของที่ร้านแก้ไม่ย้อนกลับ
   · ผลข้างเคียง: แก้ชื่อหมวดใน `seed/data.ts` แล้วรัน seed **ไม่มีผลกับฐานข้อมูลที่มีหมวดนั้นอยู่แล้ว**
   — แก้ที่ `/admin/catalog` แทน
10. **แผงกรองและตัวค้นหานับเฉพาะสี/ไซซ์ที่มีตัวเลือกขายอยู่จริง** (`SELLING_VARIANT` ใน shop.service ที่เดียว)
    — สีที่เพิ่งสร้างไม่โผล่ในตัวกรอง และค้นว่า "เสื้อสี X" ที่ยังไม่มีสินค้า ได้คำตอบว่าร้านไม่มีสีนี้
    (กฎ STEP 45 ข้อ 3) ไม่ใช่หน้าว่างที่ไม่บอกเหตุผล

## นำเข้าไฟล์ใช้กฎเดียวกัน

| กรณี                                | เดิม                               | ตอนนี้                                                    |
| ----------------------------------- | ---------------------------------- | --------------------------------------------------------- |
| สี/ไซซ์ที่ไม่มีในระบบ               | ข้ามไปเงียบ ๆ (ได้ตัวเลือกไม่มีสี) | ผิดที่แถวนั้น · เว้นว่าง = ตั้งใจไม่ระบุ                  |
| หมวด/แบรนด์/สี/ไซซ์ที่ปิดอยู่       | ผ่าน                               | ผิดที่แถวนั้น พร้อมชื่อ                                   |
| ไม่ระบุสถานะ                        | `ACTIVE`                           | สินค้าใหม่ = `DRAFT` · สินค้าเดิม = **คงสถานะเดิม**       |
| `ACTIVE` แต่สินค้ายังไม่มีรูป       | เปิดขายแบบไม่มีภาพ                 | ผิด (กฎ STEP 14 ข้อ 4) — นำเข้าเป็น DRAFT แล้วเพิ่มรูป    |
| เปิดขายสินค้าเดิมครั้งแรกจากไฟล์    | `publishedAt` ว่าง                 | ตั้งให้                                                   |
| มีคนปิดหมวดระหว่างตรวจไฟล์กับบันทึก | บันทึกไป                           | ทั้งไฟล์ไม่ถูกบันทึก (ทรานแซกชันเดียว) พร้อมบอกว่าอะไรปิด |

ไฟล์ตัวอย่างที่ดาวน์โหลดได้เปลี่ยนสถานะตัวอย่างเป็น `DRAFT` ตามกฎนี้

## ทำไมไม่สร้าง `/api/brands`

แบรนด์ที่หน้าร้านต้องใช้อยู่ใน `GET /api/products/filters` แล้ว (นับเฉพาะสินค้าที่ขายอยู่)
endpoint ที่สองที่นับแบรนด์ด้วยเกณฑ์ของตัวเองคือที่มาของตัวเลขสองชุดที่ไม่ตรงกัน (บทเรียนนโยบายสองชุดของ STEP 21)
· ฝั่งจัดการอยู่ที่ `/api/admin/catalog` · `GET /api` จึงไม่มีกลุ่มที่ประกาศว่า "กำลังจะมี" อีก

## สิทธิ์

| ทำอะไร                              | สิทธิ์                          |
| ----------------------------------- | ------------------------------- |
| ดูรายการ การใช้งาน และเหตุผล        | `product:read` (EMPLOYEE มี)    |
| เพิ่ม · แก้ · ปิด · ลบ · เรียงลำดับ | `catalog:manage` (ADMIN ขึ้นไป) |

`catalog:manage` อยู่ในข้อมูลตั้งต้นของสิทธิ์มาตั้งแต่ commit แรก (ไม่มีโค้ดไหนใช้จนถึง STEP นี้)
— ฐานข้อมูลที่เคยรัน seed แล้วมีสิทธิ์นี้อยู่แล้ว **ไม่ต้องรัน seed ซ้ำ** · การเปลี่ยนหมวดหรือปิดสี
เปลี่ยนโครงของหน้าร้านทั้งร้าน จึงไม่ใช่งานของพนักงานหน้าร้าน (แพตเทิร์นเดียวกับ STEP 17 ข้อ 8)

migration `20261008110000_variant_color_size_restrict` — เปลี่ยน FK ของ `ProductVariant.colorId` และ
`sizeId` จาก `SET NULL` เป็น `RESTRICT` · ไม่มีคอลัมน์ใหม่ — `isActive` (ทุกตาราง) · `sortOrder`
(หมวด ไซซ์ สี) · `deletedAt` (หมวด แบรนด์) มีอยู่ใน schema ตั้งแต่ migration แรก แต่ไม่มีหน้าไหนแก้ได้

## ยังไม่ได้ทำ (บอกไว้ตรง ๆ)

- **ยังย้ายสินค้าทั้งหมวดไปหมวดอื่นทีเดียวไม่ได้** — ต้องแก้ทีละชิ้นที่หน้าแก้ไขสินค้า หรือนำเข้าไฟล์ที่เปลี่ยนหมวด
- **ยังไม่มีรูปหมวดหมู่ที่อัปโหลดได้** — `Category.imageUrl` แก้จากหน้านี้ไม่ได้ (ยังไม่มี STEP ไหนรับงานนี้ไว้ ·
  ถ้าทำ ต้องผ่าน `storeImage()` ของ STEP 47)
- **รวมสองรายการเป็นรายการเดียวไม่ได้** (เช่น "ดำ" กับ "Black" ที่สร้างซ้ำ) — ต้องย้ายตัวเลือกเอง แล้วปิดอันที่ไม่ใช้
- **cache ของหน้าร้านยังหมดอายุด้วยเวลาเท่านั้น** (`revalidate: 60`) — ปิดหมวดแล้วหน้าร้านอาจยังแสดงหมวดนั้นได้ถึง 60 วินาที
  (หัวข้อ cache ของ STEP 34 · ยังไม่มีใครเรียก `revalidateTag()`)
